# Designs (contract) — legacy metadata upgrade review

`sp:spur-doctor` read-only review of the `docs/design/*.md` satellites classified as record type
`contract` (frozen list of 71 designs split by record type; the other group has its own report), against the
[authoring guide](../../plugins/sp/skills/spur-dev/references/document-authoring.md) frontmatter
vocabulary and legacy upgrade rules. Proposals only.

**Coverage:** 30/30 scanned · 30 metadata proposals · 30 with an operator question ·
0 body rewrites · 0 no-ops. Every satellite already has a `04_DESIGN.md` pointer. Bodies, headings,
anchors and inline status lines stay unchanged; `created_at` is the earlier of a body `Date` and the
first commit.

## Operator questions

| Id | Question | Recommendation | Rows |
| --- | --- | --- | --- |
| DQ1 | An explicit body owner line (`**Feature:** X`, `Feature: X`, H1 "(feature X)") naming an existing `docs/features/` record — accept as `related`? `R2` in `feature-tree-status-affordance.md` has no record and is excluded. | Accept; same basis as plan Q1. | 6 |
| DQ2 | Design status mapping: built/implemented/shipped/shipped-design/landed/done → `implemented`; accepted/approved (incl. "not yet built") → `accepted`; proposed/draft → `proposed`; a Superseded banner → `superseded` even when an older line says built. A legacy frontmatter `status` value such as "built (2026-09-22, server 803c51d09…)" is replaced, losing its parenthetical. | Accept. | 15 |
| DQ3 | Mixed or qualified statuses (partly landed, "in flight", "Design v0.1 step 2 of 6", "current audit baseline + built", "historical analysis plus current contract"). Proposed: partly landed → `accepted`; describes current behavior → `implemented`; step-in-a-derivation draft → unset. | Accept the per-row values. | 3 |
| DQ4 | No stated status. The nine 2026-09-09 contract satellites split out of `04_DESIGN.md` document current behavior → `implemented`; every other status-less design stays unset. | Accept. | 12 |
