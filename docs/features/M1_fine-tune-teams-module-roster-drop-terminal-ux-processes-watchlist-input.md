# M1: Fine-tune Teams module (Roster drop, Terminal UX, Processes watchlist, input)

## Goal

Make the Teams module in the Spur Board the direct, intuitive surface for selecting and attaching to team members, controlling their lifecycle, observing all harness-launched processes via a watch list, and interacting via terminal with visible, effective input — without requiring a prerequisite Roster tab switch.

## Scope
**In scope:**
- Drop the Roster tab entirely from Teams (TEAMS_TABS).
- Terminal tab owns its own local team/member dropdown pickers in the toolbar (sourced from `.spur/config.yaml` `agent.team.*` + live status enrichment from `/api/team/teams`); status badge + toggle (confirm on transition from running).
- Terminal input always performs local echo in the output view; for default `agent loop` members, the submitted line is also enqueued as an inter-agent message (visible in Messages, will be drained); raw `writeStdin` path preserved for custom commands.
- Add a Processes tab to Teams as the enhanced process watch list (initially supervisor processes; target = all processes created through ProcessExecutor).
- Messages tab becomes unfiltered (shows activity across members for now; filtering deferred).
- Selection state for Terminal is local to the Terminal view (does not drive Messages or Processes).
- Polish captured: localStorage persist of last Terminal selection, restart action near status, improved empty states/headers/banners, better composed-id + spec display.
- Upstream coordination note for `@gobing-ai/ts-runtime` (and ts-ai-runner) to expose a registry/observable of ProcessExecutor spawns with sufficient metadata for the watch list.

**Out of scope:**
- Re-implementing the old Roster list 1:1 or keeping it as a tab.
- Full PTY / xterm.js interactive terminal (explicit fog; line-framed SSE + stdin stays).
- Deep changes to agent loop stdin consumption (we chose message-enqueue + echo over modifying the loop for this increment).
- Altering the core message bus, supervisor ring-buffer, or ProcessExecutor implementation details beyond what's needed for listing.
- Any server multi-instance or remote process tracking.
- Changes to Observability board (system-wide tree view can stay or be adjusted independently).

## Notes

### Destination
Fine-tune the Spur Board Teams module so that attaching to member terminals is direct and intuitive, terminal input has visible + effective behavior, a comprehensive watch list of all harness-launched (ProcessExecutor) processes lives inside Teams, bulk and per-member controls are preserved without the Roster, and the previous counter-intuitive "select in Roster then switch" flow is eliminated.

### Decisions so far (locked during dev-brainstorm grilling 2026-07-14)
- Roster tab: drop entirely. Its unique operational value (grouped list + Up/Down + per-member Start/Stop + autostart hints + live status) will be redistributed: pickers + per-member status into Terminal toolbar, bulk controls into Processes (or a companion control surface), quick actions where needed.
- Terminal toolbar (replaces inner static header): Team dropdown (from agent.team keys) + cascading Member dropdown (composed ids from member list, enriched with runtime status from existing /team/teams). Status badge + toggle button with confirm modal when stopping a running process.
- Terminal member selection is **local** to the Terminal tab only.
- Messages tab (current stage): show all messages across members; no per-member filter required yet (add later when volume justifies).
- Processes tab: added to Teams. Watch list purpose. Scope target = every process created via ProcessExecutor (not just the old serve-rooted ancestor+descendants tree, and not only supervisor-tracked). This requires upstream registry/listing support in `@gobing-ai/ts-runtime` (and potentially ts-ai-runner) in `~/xprojects/ts-libs`. v1 can show supervisor processes while the upstream lands.
- Terminal input root cause + fix: default members are `spur agent loop` (which never reads its stdin; only drains DB inbox). Fix = always local echo on submit + for loop agents also `POST /messages` (enqueue as operator-to-member message) so the line becomes visible work + will be drained on next iteration. Continue to call existing writeStdin (harmless/no-op for loop, useful for custom `command:` members).
- Shared state: current TeamsContext (selectedTeamId/selectedMemberId + select) was only used to couple Roster → Terminal/Messages. After changes it can be simplified or split; Terminal will manage its own selection state.
- Polish included in this wave: localStorage persist of Terminal's last team+member choice; restart action alongside status; improved empty states, headers, error banners (e.g. "no teams configured in .spur/config.yaml"); surface composed id + source info.
- Upstream accepted: we will do (or coordinate) work in the ts-libs repo to give ProcessExecutor (or a thin registry wrapper) the ability to enumerate all its spawns with metadata (requester, label, timestamps, optional team association).
- No change to core supervisor ring buffer, message queue, or the self-draining loop model for this increment.

### Not yet specified (the fog — broad, first-pass breadth-first)
- Exact shape of the ProcessExecutor registry API / events (global singleton? context-scoped? what metadata fields? retention policy? how to tag a spawn with team context when the spawn site is deep in planning/agent-run?).
- How Processes tab will (or will not) offer inline controls (start/stop/restart) vs. being read-only observation + "attach" affordance that populates Terminal.
- How to associate non-supervisor ProcessExecutor spawns (one-shot planning runs, etc.) with a team or member for filtering/grouping in the watch list.
- Concrete confirm dialog wording, iconography, and "don't ask again" behavior (if any) for the status toggle.
- Whether a small always-visible "Team Control" strip/panel (for Up/Down bulk actions that Roster used to own) is needed in addition to per-member actions in Processes/Terminal, or whether Processes rows + Terminal toolbar suffice.
- Interaction model with the emerging Workspace module (G3) — do workspaces own a filtered view of the same teams/processes?
- Migration / back-compat for any persisted tab state or user muscle memory around "go to Roster first".
- How the web client will read the declarative team structure (currently only the server enriches /api/team/teams; do we need a direct "config teams" endpoint or can the client parse a served manifest?).
- Test surface for the new dropdowns + cross-tab behavior (current tests heavily exercise Roster selection).
- Rollout vs. the rest of the M feature work and any in-flight 025x tasks.

### Out of scope (explicitly not part of this map)
- Replacing the line-framed SSE terminal with a real PTY + xterm.js (called out as deferred in the original team design docs).
- Adding a full stdin reader + command parser inside the `agent loop` wrapper (we chose the lighter message-enqueue path).
- Any modification to the durable message queue, TeamOrchestrator, drain logic, or supervisor restart/backoff policy.
- Observability module changes (the serve-rooted process inventory can remain for system-wide use or be deprecated independently).
- Remote, multi-host, or containerized agent processes.
- Auth / access control model for the attach surfaces (assumes current local server posture).
- New config schema changes (the existing `agent.team` shape is the source of truth).
- Comprehensive AC or decomposition for the upstream ts-libs work (that will live in the ts-libs repo's own planning).
