# G91: Cross-project A2A delegation through the gateway

## Goal

Let an agent in one local project delegate work to a fleet member of another local project over A2A through the gateway, with the request tracked as a receipt until it completes, so upstream fixes (ts-libs) and release ripples (superskill install) stop depending on manual repo switching.

## Scope

**In scope**
- Cross-project fleet member declared as `{ project, member, authEnv }`, resolved at dispatch to the gateway card URL `/<prefix>/a2a/members/<slug>-<member>`; the card origin honors gateway forwarded headers so later calls stay on the gateway port.
- Refresh-on-read of existing sender-side `coordination_runs` receipts (remote task id already stored) via A2A GetTask, surfaced in `spur agent trace`.
- Two shipped delegation workflows: upstream facade fix request to ts-libs, plugin install sync request to superskill.

**Out of scope**
- Remote-host delegation (ADR-151).
- A new inbox writer or table (ADR-143).

## Acceptance Criteria

```gherkin
Feature: Cross-project A2A delegation through the gateway

  @core
  Scenario: R1 — A cross-project member address resolves through the gateway
    Given two local projects behind the gateway, the target with A2A enabled
    When an agent dispatches to a fleet member declared with that project and member
    Then the request reaches the target member inbox through /<prefix>/a2a with the target token and returns a task id

  @core
  Scenario: R2 — Delegated work is tracked as a receipt until terminal
    Given a delegated cross-project request
    When the sender inspects it later
    Then the local coordination_runs receipt shows the remote task id and its current state from GetTask, ending at a terminal state

  @edge
  Scenario: R3 — Upstream and release-ripple delegations ship as workflows
    Given the two delegation workflows
    When they run against fixture projects
    Then a task is created in the target project and the receipt links back to the requesting task

```
