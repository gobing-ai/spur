# G9: Cross-machine fleet: spur serve speaks A2A

## Goal

Let a Spur install on one machine hand work to fleet members on another, with Agent2Agent (A2A) v1.0 as the only wire between them and the inbox as the durable record at both ends. `spur serve` presents each live member as an A2A agent; the sending side needs nothing new beyond a member declared with that card (G8). The user still only names an agent.

## Scope

**In scope**

- An opt-in A2A v1.0 HTTP+JSON endpoint on `spur serve`, off by default, with one Agent Card per live fleet member.
- `SendMessage` turned into one keyed inbox request (`messageId` becomes the request key); `GetTask` answered from the run receipt; `CancelTask` stopping the run.
- Bearer-token authentication for the endpoint, with the token read from an environment variable.
- An end-to-end proof: two Spur installs complete a dispatch across the A2A wire using the `a2a` member declaration from G8.
- A card extension by which a Spur member declares that it fences its own working tree, so the sender may give it worktree-mutating work.
- A design-satellite section and an ADR-148 amendment for the listener.

**Out of scope**

- Any change to how a user dispatches work (G8 owns that).
- Returning the remote working-tree changes to the sender; the sender receives artifact text and the remote branch name.
- Streaming, push notifications, gRPC and JSON-RPC bindings, multi-turn input round trips.
- TLS termination and multi-tenant access control; the endpoint binds to the configured `server.host` and relies on the operator's network boundary.
- Discovery of remote installs; the sender declares the card URL.

## Acceptance Criteria

```gherkin
Feature: Cross-machine fleet: spur serve speaks A2A

  @core
  Scenario: R1 — A live member is published as an A2A Agent Card
    Given spur serve running with the A2A endpoint enabled and a live member named coder
    When an A2A client fetches the card for coder
    Then the card reports protocol version 1.0, the HTTP+JSON interface and the member's name

  @core
  Scenario: R2 — An A2A message becomes one keyed inbox request
    Given the A2A endpoint enabled and a live member
    When a client sends the same message id twice
    Then exactly one inbox request exists for that message id
    And both responses carry the same task id

  @core
  Scenario: R3 — Task state is read from the run receipt
    Given a task created through the A2A endpoint
    When the member's run completes, fails, or is still running
    Then GetTask reports completed with the answer as an artifact, failed with the reason, or working
    And the state survives a spur serve restart

  @core
  Scenario: R4 — Canceling the task stops the run
    Given a task whose run is in progress
    When the client cancels the task
    Then the run stops and GetTask reports canceled

  @core
  Scenario: R5 — The endpoint is off by default and refuses unauthenticated callers
    Given a default configuration
    When a client calls any A2A route
    Then the route does not exist
    And with the endpoint enabled a call without the configured token is rejected and enqueues nothing

  @core
  Scenario: R6 — Two Spur installs complete a dispatch over A2A
    Given install A declaring a member with the card served by install B
    When a user on A dispatches a read-only prompt to that member by name
    Then B's member runs it and A's receipt is completed with B's answer
    And each install holds its own durable record of the work

  @extended
  Scenario: R7 — A member that declares its own write fencing accepts mutating work
    Given a remote card carrying the Spur write-fencing extension
    When worktree-mutating work is dispatched to that member
    Then it is accepted, runs in the remote member's working tree, and the receipt names the remote branch
    And the same work sent to a card without the extension is still refused
```
