# J7: Board surfaces for role routing and token consumption

## Goal
The Board shows **how work is being routed and what it consumes** — which executor served which
role, how often routing had to escalate, and the token totals behind it.

Feature J6 (batch 2) ships the data: the routing decision on every run, a queryable
role-to-executor aggregate, and token totals joined over `run_id`. J6's scope deliberately excludes
rendering it, because feature J4 owns Board surfaces. This feature is that rendering.

Without it the routing data is reachable only by query, which means in practice it is not looked at —
and a `scribe` role quietly served by a `capable-3` executor stays invisible for exactly as long as
nobody runs the query.
## Scope
- In:
    - A Board surface for the role-to-executor routing aggregate: run counts, escalation counts, and
      the selection source split (role-resolved versus pinned).
    - Token totals per role — input, cache-read, cache-write, output — rendered alongside, with
      unmeasured and estimated states shown as themselves.
    - Reuse of the existing Board module patterns and observability surfaces established by J4.
- Out:
    - Any dollar figure. Excluded permanently by operator ruling 2026-08-13 (feature J6 §
      *Tokens, not prices*); per-model pricing is too volatile to hold correctly.
    - Producing the data. Feature J6 tasks 0545/0546/0547 own emission, aggregation, and the token
      join; this feature renders what they expose and adds no query of its own.
    - New observability tables, columns, or transports.
    - A new Board module. This extends existing surfaces rather than adding a peer to Teams and
      Observability.

## Notes
### Sequencing

Blocked on feature J6 (batch 2) tasks 0546 and 0547, which expose the aggregate and the token totals.
Building the surface first would mean designing against a shape that does not exist yet.

### Render the honest states, not just the happy one

Three of this feature's four scenarios are about **not lying with a number**, which is deliberate.
The underlying data carries distinctions that are easy to flatten in a UI and expensive to flatten:

- *unmeasured* (no matched history rows) is not *zero* — task 0547 R3 and the never-fabricate
  invariant at `packages/domain/src/analytics/run-cost.ts:240`
- *estimated* (time-window join) is not *exact* (`run_id` join) — task 0547 R4
- *no data yet* is not *no activity*

A dashboard that renders all of these as `0` is worse than no dashboard, because it converts a known
gap into an apparent measurement.

### Boundary

Feature J4 (done) owns Board observability and Teams supervisor surfaces; M3 owns Teams UX. This
feature extends what they established rather than adding a peer module.
