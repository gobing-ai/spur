# A6: Harness trust and operational controls

## Goal

Make Spur's harness completion claims and unattended execution controls mechanically trustworthy: a PASS names one
immutable proof state, every constrained executor stage proves the native controls it relies on, runtime limits stop at
safe boundaries, escalation is actionable, review is independent, memory is fresh, and operational success is measured
as verified outcomes rather than activity.

## Scope

**In scope**

- Task and docs workflow verdict integrity using the existing proof fingerprint, verdict, and completion-gate surfaces.
- A deterministic UTF-8 byte sensor for always-loaded project and portable AGENTS guides.
- Fixed executor capability attestations and per-stage requirements at the current config/`agent.run` seam.
- Honest typed live usage propagation and hard token/cost enforcement at supported safe boundaries.
- A fixed initial trip-wire catalog and canonical escalation projection over current events/artifacts.
- Fresh-context review/verification plus risk-tiered distinct executor enforcement.
- Versioned checkpoint/index freshness and bounded cleanup through current memory owners.
- Verified-result, correction, duration, and attributable-cost metrics through existing history analysis.

**Out of scope**

- A new workflow engine, agent framework, sandbox implementation, policy DSL, vector database, billing platform, remote
  control plane, external ticketing integration, or public CLI noun.
- Automatic rollback, unbounded repair, fabricated token/cost estimates, model-based trip-wire decisions, or automatic
  deletion of authoritative/operator-authored memory.
- Copying the source PDF's architecture. Each delivery extends Spur's current seams and preserves its local-first,
  native-agent, Markdown/SQLite authority model.

## Acceptance Criteria

```gherkin

  @core
  Scenario: R1 — PASS certifies one unchanged state
    Given quality, review, verification, and completion operate on one task

  @core
  Scenario: R2 — Satisfied docs task completes
    Given a docs-only deliverable satisfies its requirements and acceptance criteria
    When docs-pipeline completes
    Then its PASS is derived from measured read-only verification rather than a synthetic artifact

  @core
  Scenario: R3 — Current guides retain headroom
    Given the root and portable always-loaded guides
    When repository contract checks run
    Then each remains within the deterministic UTF-8 byte budget

  @core
  Scenario: R4 — Sufficient enforced capability dispatches
    Given an unattended stage declares native execution-control requirements
    When an executor is resolved
    Then dispatch occurs only when its attestation satisfies every required control

  @core
  Scenario: R5 — Measured usage is propagated
    Given a native runner reports structured usage
    When an agent action completes
    Then Spur preserves the measurement and enforces declared hard budgets without fabricating unavailable values

  @core
  Scenario: R6 — Known invariant stops the run
    Given a retry, budget, capability, proof, or output invariant crosses its fixed trip-wire condition
    When the workflow reaches the next safe boundary
    Then the run fails closed and dispatches no subsequent action

  @core
  Scenario: R7 — Trip wire creates one actionable packet
    Given a run stops on a trip wire or eligible terminal failure
    When escalation is recorded
    Then one bounded redacted packet references existing evidence and states the unresolved operator decision

  @core
  Scenario: R8 — Reviewer starts without implementation context
    Given implementation has a resumable conversation session
    When review or final verification starts
    Then it uses fresh context and material-risk work uses a distinct eligible executor

  @core
  Scenario: R9 — Fresh checkpoint resumes
    Given a resumability checkpoint and indexed context are schema-valid and current for their source state
    When routing or cleanup evaluates them
    Then only fresh state is consumed and only expired unreferenced regenerable memory is deleted

  @core
  Scenario: R10 — Clean verified result is counted
    Given a task completes through a proof-valid PASS without later correction
    When history analysis covers the run
    Then verified-result, correction, duration, and attributable-cost metrics report it with explicit coverage
```
