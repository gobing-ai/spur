# K44: One MCP config for gateway and projects; one A2A member list

## Goal

Make agent-protocol setup one decision per surface. MCP gets one config block and one token for the
gateway root `/mcp` and every project's `/<prefix>/mcp`; the Board shows A2A as one member list
with a direction instead of two lists. Operator-approved 2026-11-25: the separate gateway MCP
credential (ADR-151 K41) protected no real boundary, because the gateway proxies `/<prefix>/mcp`
on the same origin and every project reads the same global `server.mcp.authEnv`.

## Scope

- In: remove `server.gateway.mcp` and `SPUR_GATEWAY_MCP_*`; the gateway root `/mcp` and `spur mcp --gateway` read `server.mcp`; the Integrations contract keeps `gateway.mcp` only as the running gateway's probed runtime state (never config); plugin MCP manifest, seeded global config, install guide, design satellites and ADR-151/152 amendments follow.
- In: Integrations contract replaces `a2a.inbound` + `a2a.outbound` with one `a2a.members[]` carrying `direction`; the A2A tab renders one members list labelled by direction.
- Out: merging the project and gateway processes (ADR-151 keeps per-project process isolation); new MCP tools; A2A config shape (already one listener plus one member list).

## Acceptance Criteria

```gherkin
Feature: One MCP config for gateway and projects; one A2A member list

  Scenario: R1 — One server.mcp block drives both MCP endpoints
    Given a config with server.mcp enabled and no server.gateway.mcp block
    When the gateway starts and an agent runs spur mcp --gateway
    Then the gateway root /mcp is on and authenticates with the variable server.mcp.authEnv names

  Scenario: R2 — The gateway MCP config surface is gone
    Given a config that still carries server.gateway.mcp or SPUR_GATEWAY_MCP_* variables
    When the config loads
    Then those keys have no effect and server.mcp alone decides the gateway root /mcp

  Scenario: R3 — The Board shows A2A members in one list
    Given a project with a receive-capable member and an outbound peer
    When the Integrations A2A tab renders
    Then both appear in one members table, each labelled inbound or outbound
```
