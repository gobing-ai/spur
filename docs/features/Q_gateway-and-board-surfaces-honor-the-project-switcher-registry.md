# Q: Gateway and Board surfaces honor the project switcher registry

## Goal

Make the one-port project gateway and every surface that reads the project registry agree on which
entry owns a route and how to reach it: a local project is reachable at `/<prefix>/board` regardless
of which loopback family its serve bound, a second entry for the same path on another host cannot
capture that route, and misconfiguration or staleness in the registry is reported to the operator in
the CLI and the Board instead of surfacing as a bare 502 or a list of dead rows.

## Scope

**In scope**

- Gateway upstream dialing that works for a local serve bound to `127.0.0.1` and to `::1`, using the
  existing both-families loopback probe as the reachability contract.
- Upstream adoption and proxy routing keyed by the registry entry the prefix belongs to (path and
  host), so a duplicate path on another host cannot supply the port for a local prefix.
- `spur projects list` human output: no unroutable URL for a stopped entry, and the resolved prefix
  shown as its own field.
- Board visibility for prefix collisions and duplicate-path entries that would make a route fail.
- Registry staleness visibility and removal for entries `projects clean` does not catch (ephemeral
  project roots that still exist, duplicate paths).

**Out of scope**

- Registry file format or `schema_version` changes; `prefix` stays a local-only optional field.
- Autonomous deletion of operator entries without an explicit invocation.
- Remote-entry routing through the gateway, tunnels, or multi-tenant hosting.
- Replacing per-port Board access; it stays a supported fallback.

```gherkin
  When the gateway receives GET /credit-sentry/board
  Then the gateway proxies the request and answers 200 with the project's Board document

  @core
  Scenario: R3 — A second entry for the same path on another host cannot capture a local prefix
  # covers: I2

  And a remote entry for the same path with host "192.168.87.27" and port 3003
  When the gateway receives GET /knowledge-kit/board
  Then the gateway dials the local entry's port 3007
  And it never dials the remote entry's port 3003 for that prefix

  @core
  Scenario: R4 — An unreachable upstream is still reported as unreachable
  # covers: I1
  Given a local project with prefix "/ts-base" whose serve is stopped on every loopback family
  When the gateway receives GET /ts-base/board
  Then the gateway answers 502 naming the project and the port it dialed
  And the reply points at the project's serve spawn log

  @core
  Scenario: R5 — projects list reports the route instead of an unroutable URL
  # covers: I3
  Given a registered project "Treasury" with prefix "/treasury" and port 0
  When the operator runs spur projects list
  Then the output shows the prefix "/treasury" for that entry
  And the output does not print a url containing port 0

  @core
  Scenario: R6 — The Board reports a prefix collision instead of failing the route silently
  # covers: I4
  Given two local entries that resolve to the prefix "/b"
  When the operator opens the projects module on the Board
  Then the Board renders a warning naming both entries and the colliding prefix
  And the warning states the remedy of setting one entry's prefix

  @core
  Scenario: R7 — Registry staleness is visible and removable
  # covers: I5
  Given a registered project whose path is an ephemeral test directory that still exists
  When the operator runs the registry staleness check
  Then the entry is listed as suspect with its path
  And passing the removal flag removes exactly that entry and leaves every other entry in place
```
