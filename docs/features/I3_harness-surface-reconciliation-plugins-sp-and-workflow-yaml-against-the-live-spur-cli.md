# I3: Harness surface reconciliation: plugins/sp and workflow YAML against the live spur CLI

## Goal
`plugins/sp` and `config/workflows/*.yaml` are reconciled against the **live** `spur` CLI surface, so
that every flag, verb, and tier fact a command or workflow asserts is one that actually exists and
behaves as described.

Both trees are tightly coupled to a CLI that has moved underneath them. B2's migration (task 0538)
fixes the one class of drift the intention layer forces — duplicated tier prose. This feature sweeps
for the rest, and hardens the tier-fallback path that has shipped but never been exercised under real
failure.

Sequenced **after** B2/0538 deliberately: an audit run before the migration would inventory drift that
the migration is about to remove, and would miss the drift the migration exposes.
## Scope
- In:
    - A reproducible inventory of drift between `plugins/sp` (commands, skills, references, scripts,
      hooks) and the live `spur` CLI surface: flags that no longer exist, verbs renamed, `--json`
      shapes changed, documented behavior that no longer holds.
    - The same inventory for `config/workflows/*.yaml` — step kinds, action inputs, vars contracts,
      and the `.spur/workflows` symlink path model.
    - Fixing the confirmed defects the inventory finds, or filing them as tasks when a fix is larger
      than the sweep.
    - Tier-fallback exhaustion behavior under real failure: what happens when the starting tier fails,
      when every eligible executor is exhausted, and when a fallback target is unreachable.
- Out:
    - Feature B2's intention layer and its migration — this feature consumes B2's result, never
      redoes it.
    - Redesigning the `spur` CLI surface. Drift is fixed by correcting the plugin or the workflow;
      changing a CLI noun or verb requires operator consent under ADR-051 and is a separate ask.
    - `superskill`-owned per-platform adapter generation.
    - Rewriting workflow *semantics*; this is reconciliation against the existing engine, not a new
      execution model.
## Acceptance Criteria
```gherkin
Feature: Harness surface reconciliation

  @core
  Scenario: R1 — Plugin assertions are inventoried against the live CLI
    Given plugins/sp asserts spur flags, verbs, and --json shapes across commands, skills, and scripts
    When each assertion is checked against the installed CLI surface
    Then every mismatch is recorded with the file, the line, the asserted form, and the actual form
    And an assertion that cannot be checked mechanically is recorded as unverified rather than as passing

  @core
  Scenario: R2 — Workflow YAML is inventoried against the live engine
    Given config/workflows carries ten workflow definitions
    When each step kind, action input, and vars contract is checked against the engine
    Then every mismatch is recorded with the workflow, the step, and the divergence
    And the .spur/workflows symlink is confirmed to resolve to the tracked config/workflows tree

  @core
  Scenario: R3 — Confirmed drift is repaired or filed, never left recorded-and-ignored
    Given the inventory lists confirmed mismatches
    When the sweep completes
    Then each entry is either fixed in this feature or carries the WBS of the task that owns it
    And no confirmed entry ends the feature in neither state

  @core
  Scenario: R4 — Tier fallback is exercised under real failure, not asserted
    Given a stage whose starting-tier executor fails on an objective signal
    When the run escalates
    Then the next eligible executor by the declared fallback chain runs
    And the transition is observable in the run record with the trigger that caused it

  @core
  Scenario: R5 — Executor exhaustion fails loudly
    Given every executor eligible for a stage has failed
    When no fallback target remains
    Then the run exits non-zero naming the stage, the tiers attempted, and the executors tried
    And it does not silently fall through to agent.default or to a bare binary

  @edge
  Scenario: R6 — An unreachable fallback target is distinguished from a failed one
    Given a fallback tier for which no executor is configured
    When escalation reaches that tier
    Then the run reports the fallback as unreachable, naming the tier
    And it continues to the next reachable tier rather than terminating as exhausted
```

## Notes
### Sequencing

Blocked on feature B2's task 0538 (the intention migration). Starting earlier inventories drift that
0538 is about to delete and misses the drift 0538 exposes.

### Prior art

`I2` (spur-dev/spur-cli parity-first drift audit and harness refinement, done) is the previous pass of
this same sweep. Read its findings and its method before re-deriving one — this feature is the next
iteration of an established audit, not a new technique.

### Why the fallback half sits here and not in B2

Tier fallback shipped through H9/0407 and was extended by 0482 and 0485 (all done), but the operator's
standing observation is that it has never been exercised well under real failure. That is hardening of
an existing mechanism rather than part of B2's selection redesign, and it shares this feature's
evidence base — runtime behavior of the harness as installed.
