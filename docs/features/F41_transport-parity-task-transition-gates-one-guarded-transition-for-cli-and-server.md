# F41: Transport-parity task transition gates: one guarded transition for CLI and server

## Goal

A task status transition passes the same done/testing gates whichever transport requests it. Today the
structural check gate (`spur task check --as <status>`) and the done-verdict gate (task 0292,
`.spur/run/<wbs>-verdict.json`) run only inside the CLI command (`apps/cli/src/commands/task.ts:590-700`).
The server's `task.transition` handler (`apps/server/src/modules/task/handlers.ts:87-90`) calls
`TaskServiceImpl.updateStatus` directly, where the `SchemaLifecyclePort` stub only rejects a same-status move —
so a Kanban drag moves a task to `done` with no PASS verdict and with L3 findings open.

The gates move into one guarded transition in `packages/app` (ADR-021: apps are thin transports). The CLI and
the server both call it. The section-matrix loader, duplicated today between the CLI (`task.ts:1864-1900`,
schema-validated) and the server (`serve.ts:70`, unvalidated), moves with it.

Source: `/sp:dev-review apps --focus all` (2026-09-25), findings P2 (server bypasses done gates) and C2
(gate logic lives in a transport); base commit `872024cd2`.

## Scope

- In: a guarded transition function in `packages/app/src/services/`; a shared section-matrix loader in
  `packages/app`; the CLI `task update <wbs> <status>` path (`apps/cli/src/commands/task.ts`) and the server
  `task.transition` handler rewired onto it; server context wiring (`apps/server/src/context.ts`,
  `apps/server/src/serve.ts`); tests in the three workspaces.
- Out: the `task.transition` oRPC contract (`packages/contracts/src/task.ts:74` stays `{wbs, toStatus, actor?}`
  — no `forceDone` over HTTP; adding one needs operator consent); `spur task` flags and CLI output text;
  the lifecycle workflow YAML and `makeLifecycleAdapter`; `evaluateDoneTransition` / `readVerdictArtifact`
  semantics; the Kanban UI (it already reverts on error, `KanbanBoard.tsx:196`); `task-readiness.ts:235`
  (`→ todo`, ungated by design).
