# B7: Run-scoped executor session: resolve once per run, pin across stages, per-stage fresh-session policy

## Goal

A pipeline run resolves its executor once per role and reuses that executor's session across the model-bearing stages that may share it, so stages stop paying the cold-context cost of a fresh subprocess; sharing is a declared per-stage policy, and reviewer stages never inherit the coder's session by default.

## Scope

- In:
  - **Resolve once.** Precheck resolves the executor for each declared role once and pins it into run vars; later `agent.run` stages consume the pin and never re-enter doctor/detection.
  - **Session pin per role.** The existing `__agentSessionDir` / `__agentSessionId` affinity vars become per-role pins carried across stages.
  - **Per-stage policy.** Workflow YAML stages declare `session: reuse | fresh`. Defaults: coder-role stages reuse; reviewer/verify-role stages are fresh; reuse on a reviewer stage must be explicit.
  - **Degradation.** An executor whose agent cannot resume by id runs fresh per stage and warns once per run naming the executor and the missing capability.
  - **Pin invalidation.** If the pinned executor becomes disabled mid-run (B6), the next stage re-resolves once, logs the reason, and starts a fresh session on the new pin.
  - **Trace.** `spur workflow trace` shows executor, session id and `reused|fresh` per `agent.run` stage; E6 records an exact mapping whenever the session id was supplied.
- Out:
  - Runner capability declarations — feature B8 (B7 reads them once present; until then it uses the runner's current affinity matrix).
  - Fleet member loops — feature G66.
  - Inline driver semantics (the host session is already one session).
  - Any change to ADR-118 stage contracts or ADR-119 gate scope.

## Acceptance Criteria

```gherkin
Feature: Run-scoped executor session

  @core
  Scenario: R1 — Executor resolution happens once per role per run
    Given a task-pipeline run started with --agent auto
    When the precheck stage completes
    Then each declared role has exactly one pinned executor in the run vars
    And no later stage invokes doctor or agent detection

  @core
  Scenario: R2 — A coder-role stage resumes the previous coder-role session
    Given a pinned executor whose agent can resume a session by id
    When the implement stage completes and the test stage starts
    Then the test stage resumes the implement stage's session
    And the trace records the same session id for both stages

  @core
  Scenario: R3 — Reviewer-role stages never inherit the coder session by default
    Given a run whose implement stage produced a session
    When the review or verify stage starts
    Then it runs in a fresh session
    And the trace records a session id distinct from the implement stage

  @core
  Scenario: R4 — A stage can override the session policy explicitly
    Given a workflow stage declaring session fresh on a coder-role stage
    When that stage runs
    Then it starts a new session regardless of the pinned session
    And a reviewer-role stage declaring session reuse is the only way a reviewer shares a session

  @core
  Scenario: R5 — An executor without resume support degrades to fresh per stage
    Given a pinned executor whose agent cannot resume a session by id
    When the model-bearing stages run
    Then each stage runs in a fresh session
    And one warning per run names the executor and the missing capability

  @core
  Scenario: R6 — The trace shows executor and session per stage
    Given a completed run with several agent.run stages
    When the operator runs spur workflow trace for the run
    Then each agent.run stage lists its executor, its session id and whether the session was reused or fresh

  @core
  Scenario: R7 — A pin is re-resolved when its executor is disabled mid-run
    Given a run with a pinned executor
    When that executor becomes disabled before the next stage starts
    Then the next stage re-resolves the role once and records the reason
    And the new pin starts a fresh session

  @edge
  Scenario: R8 — Stage cost attributes to the executor through the session mapping
    Given a completed run whose stages supplied session ids
    When run-to-session correlation runs
    Then every such stage has an exact run-to-session mapping
    And per-stage token figures attribute to the pinned executor
```
