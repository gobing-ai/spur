# J94: Agent-protocol observability: MCP, A2A and auth events over one shared bearer guard

## Goal

Make every agent-facing protocol call (MCP `POST /mcp`, A2A `/a2a/*`) observable as 5W1H system events, emitted from one shared bearer-auth guard and the two protocol dispatchers, so an operator can answer who called which tool/member, with what outcome and latency, from the Board System Events view.

## Scope

**In scope**
- Extract the duplicated bearer-auth code (`requiredToken`/`authorize`/`sameToken` in `apps/server/src/modules/a2a/index.ts:55,205` and `apps/server/src/modules/mcp/index.ts:232,280`) into one guard in `apps/server/src/middleware/`, parameterized by realm, `authEnv` and error shape; token read at request time on both surfaces.
- Catalog entries + emitters: `auth.denied`, `mcp.tool.called`, `mcp.tool.failed`, `mcp.resource.read`, `a2a.message.received`, `a2a.task.cancelled`, each with an event-specific presenter per `docs/design/event-tracking.md` §3.
- E2E proof through the existing MCP and A2A e2e harnesses.

**Out of scope**
- Per-request HTTP access logging (volume without decision value).
- Persisting tool argument values or tokens (secret-bearing; only argument key names may be recorded).
- Gateway-process events (owned by the gateway observability feature).

## Acceptance Criteria

```gherkin
Feature: Agent-protocol observability: MCP, A2A and auth events over one shared bearer guard

  @core
  Scenario: R1 — One bearer guard serves both protocol surfaces
    Given server.mcp and server.a2a are enabled with their own authEnv variables
    When a request reaches /mcp or /a2a/* with a missing, wrong or valid bearer token
    Then both surfaces apply the same guard with their own realm, and answer 401 with a realm challenge, 500 fail-closed when the variable is unset, or pass through

  @core
  Scenario: R2 — Every MCP tool call and resource read emits a 5W1H event
    Given an authenticated MCP client
    When it calls a tool that succeeds, a tool that throws, or reads a spur:// resource
    Then mcp.tool.called, mcp.tool.failed or mcp.resource.read persists with tool or uri, durationMs, outcome, error code, and the related runId or wbs when present, and never an argument value

  @core
  Scenario: R3 — Refused authentication is observable without leaking the token
    Given either protocol surface is enabled
    When a request is refused by the bearer guard
    Then auth.denied persists with surface, reason (missing, mismatch, unset) and path, and no token material

  @core
  Scenario: R4 — A2A message intake and cancellation emit events
    Given the A2A listener is enabled with at least one fleet member
    When a client sends a message (new or replayed messageId) or cancels a task
    Then a2a.message.received persists with member, messageId, request key and an outcome (accepted, replayed, conflict), and a2a.task.cancelled persists with member, task id and whether a supervised run stopped (accepted cancels only)

  @edge
  Scenario: R5 — Protocol events read as sentences in the Board
    Given protocol events exist in system_events
    When the operator opens Observability System Events
    Then each protocol event renders through its own presenter with who, what and outcome columns, not the generic renderer

```
