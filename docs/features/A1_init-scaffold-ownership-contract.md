# A1: Init scaffold ownership contract

## Goal
`spur init` owns copying the complete canonical project scaffold from its bundled npm package config, and `/sp:spur-init` is a thin adapter that always invokes `spur init` first and then only adapts content — one ownership boundary, zero scaffold gaps on fresh projects.
## Scope
- In:
    - Gap audit: diff the canonical source tree (`config/` + project-root scaffolds in this repo) against what `SCAFFOLD_MANIFEST` (`apps/cli/src/config/scaffold-manifest.ts`) actually writes; known gap example — `TASK_VARIANTS` has 6 variants but only 5 task templates are scaffolded (`brainstorm.md` missing).
    - Extend `SCAFFOLD_MANIFEST` so every default a fresh project needs is copied by `spur init` (rule presets and their category dependencies, all bundled workflows, tasks/section-matrix, all task/feature/bdd/docs templates).
    - Ownership contract documented in `04_DESIGN.md`: `spur init` = file copying from the package; `/sp:spur-init` = content adaptation only (project name, docs customization), never ad-hoc file creation.
    - Rewrite `plugins/sp` `/sp:spur-init` command + `sp:spur-init` skill to call `spur init` before any adaptation step.
    - Regression tests: fresh-directory init is immediately functional for `spur task create`, `spur feature create`, `spur workflow validate`, `spur rule run`.
- Out:
    - Changes to global `~/.config/spur` seeding semantics.
    - New config surface or new scaffold content beyond parity with the canonical tree.
    - `--minimal` behavior changes (it keeps writing only the minimal `.spur/` scaffold).
## Acceptance Criteria
```gherkin
Feature: Init scaffold ownership contract

  Scenario: Fresh init writes the complete scaffold
    Given an empty project directory
    When spur init runs without flags
    Then every SCAFFOLD_MANIFEST entry exists on disk
    And .spur/tasks/templates contains one template file per TASK_VARIANTS variant

  Scenario: Fresh scaffold is immediately functional for planning commands
    Given a freshly initialized project
    When spur task create "probe" runs
    Then a task file is created without missing-template or missing-matrix errors

  Scenario: Fresh scaffold workflows validate
    Given a freshly initialized project
    When spur workflow validate .spur/workflows/task-pipeline.yaml runs
    Then the workflow is reported valid with exit code 0

  Scenario: The skill delegates scaffolding to the CLI
    Given a fresh project initialized via /sp:spur-init
    When the skill flow completes
    Then all scaffold files on disk match what spur init writes
    And only doc contents were adapted by the skill

  Scenario: Re-init preserves customized docs
    Given an initialized project with customized preserve-marked docs
    When spur init --force runs
    Then preserve-marked docs are not overwritten
```
