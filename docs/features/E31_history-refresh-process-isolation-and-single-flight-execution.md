# E31: History refresh process isolation and single-flight execution

## Goal

Keep Spur Board requests responsive while scheduled history refreshes run, and guarantee that only one refresh is pending or executing for a project at a time.

## Scope

- In:
  - Run queued history refresh work in a child process by reusing the existing `spur history daily --json` surface.
  - Enforce a database-backed single-flight invariant across scheduled, operation-completion, and manual refresh producers.
  - Preserve refresh trigger, import mode, and requested window through the queue job envelope into the child process.
  - Report enqueued, coalesced/already-running, completed, and failed outcomes through existing queue and system-event surfaces.
  - Verify Board/API responsiveness, producer races, child-process failure propagation, and SQLite contention.
- Out:
  - Rewriting the history import/analyze pipeline or changing its analytics results.
  - Adding a new public CLI noun or verb, worker daemon, external queue, dependency, or deployment unit.
  - Raising the web RPC timeout to hide event-loop stalls.

## Acceptance Criteria

```gherkin
Feature: Isolated single-flight history refresh

  @core
  Scenario: R1 — A running refresh does not block Board requests
    Given the Spur server is serving Board API requests
    And a queued history refresh child process is still running
    When the Board requests data during that refresh
    Then the requests complete before the existing web RPC timeout
    And no request fails because its abort signal timed out

  @core
  Scenario: R2 — The queue worker reuses the existing daily command in a child process
    Given a history refresh job is ready
    When the queue worker handles the job
    Then it invokes the source-local `spur history daily --json` command through the existing process executor
    And the server process does not execute import or analyze work directly

  @core
  Scenario: R3 — All producers share one pending-or-processing invariant
    Given a history refresh is pending or processing for a project
    When scheduled, operation-completion, or manual producers request another refresh
    Then no second pending refresh is created
    And no second refresh starts concurrently
    And the producer receives an observable coalesced or already-running outcome

  @core
  Scenario: R4 — Concurrent producers cannot bypass single-flight
    Given no history refresh is pending or processing
    When two independent producers enqueue at the same time
    Then the database admits exactly one pending refresh
    And both producers receive deterministic outcomes without an unhandled uniqueness error

  @core
  Scenario: R5 — Refresh intent survives the queue envelope
    Given a scheduled or manual refresh includes a trigger, import mode, and requested window
    When the queue worker starts the child process
    Then the child receives the same trigger, import mode, and requested window
    And completion telemetry reports those values rather than defaults

  @edge
  Scenario: R6 — Child-process failure fails the queue job visibly
    Given the history refresh child process exits non-zero or returns invalid JSON
    When the queue worker handles its result
    Then the queue job is marked failed and follows its configured retry policy
    And the failure is recorded through the existing system-event surface

  @edge
  Scenario: R7 — SQLite contention remains bounded and visible
    Given the server and refresh child process access the project database concurrently
    When either side encounters a lock beyond the configured busy timeout
    Then the affected operation fails with its original database error
    And the server event loop remains responsive
```
