# G71: Core inbox fleet: one dispatcher, member execution, execution record

## Goal

One fleet dispatch primitive serves workflow `agent.run --agent fleet` and the GTD strategy tick. Members drain their inbox and execute work; the orchestrator drains its own inbox before a non-blocking tick; completion is the `coordination_runs` receipt; a timeout is outcome-unknown (ADR-126 amendment). Interrupted work resumes with `--continue`. Every `spur agent run` and fleet turn records a durable stream and lineage readable by `spur agent trace` (ADR-132). Plan: `docs/plans/2026-10-04-agent-fleet-inbox-redesign.md` §3.2 items 1–6, 11, 15.

## Scope

- In: `packages/app` fleet dispatch, agent loop, strategy runtime, write slot, member session, agent service run boundary; one migration (`coordination_runs.parent_run_id`); new verb `spur agent trace` (consented, D7); `memberLocalId`; the E2E receipt script.
- Out: team residue removal (G72); hook lifecycle and guest join (G73); `MemberSession` modes and `DeliveryReconciler` hold reasons (unchanged); inline host-session output capture (ADR-129 owns it).

## Acceptance Criteria

```gherkin
Feature: Core inbox fleet: one dispatcher, member execution, execution record

  Scenario: R1 — Fleet work is dispatched only through the inbox
    Given agent.fleet is enabled
    When a workflow agent.run selects the fleet or the GTD tick selects a fleet:auto task
    Then both enqueue one keyed inbox message to the member through the same dispatcher
    And no orchestrator process runs member work in-process

  Scenario: R2 — Completion is the coordination receipt
    Given a dispatched fleet message
    When the dispatcher waits
    Then the wait is pinned to the member occupant and resolves from the coordination_runs receipt linked to the message
    And a timeout reports outcome-unknown and is never re-dispatched until a definite failed or not-started receipt exists

  Scenario: R3 — Members drain their inbox and hold the write slot
    Given a fleet member loop
    When a message arrives
    Then the member drains, executes and settles it, heartbeating the write slot while a dispatched run is live

  Scenario: R4 — The orchestrator converses through its inbox
    Given an operator message to the orchestrator
    When the orchestrator wakes
    Then it drains and replies before running the strategy tick, and the tick never blocks on member work

  Scenario: R5 — Interrupted fleet work resumes
    Given a fleet:auto task in wip or with an unfinished prior run
    When it is dispatched again or the operator messages the member
    Then the prompt carries --continue, the member resumes its last exact agent session, and no beforeDispatch guard refuses it

  Scenario: R6 — Member identity does not follow the executor
    Given a fleet member that pins an executor without an id
    When the fleet resolves member ids
    Then the id is role-based and stable, and a config relying on the old executor-derived id fails with a fix-it error

  Scenario: R7 — Every execution has a durable record
    Given a spur agent run or a fleet member turn
    When it finishes, even after a serve restart
    Then spur agent trace <runId> shows its parent lineage, its agent session ids and its stdout/stderr stream

  Scenario: R8 — The inbox-only fleet is proven end to end
    Given a scratch project with a declared fleet
    When the E2E script runs the plan §1 done scenario
    Then it writes a repeatable JSON receipt that records every step's evidence
```
