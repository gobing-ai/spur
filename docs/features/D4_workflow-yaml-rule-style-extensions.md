# D4: Workflow YAML rule-style extensions

## Goal

spur workflow validate and run load action and guard modules listed in the workflow YAML extensions block, so a definition can add kinds without changing Spur builtins.

## Scope

- In:
  - After `loadWorkflowDef`, collect `extensions.actions` / `extensions.guards` with `baseDir = dirname(workflow file)` and call `loadWorkflowExtensionsIntoHost`
  - `validate`, `run` (including `--dry-run`), and `continue` share the same load path
  - When the YAML declares any extension ref, CLI sets `allowExtensions: true` (the declaration is the trust decision; paths stay confined to the YAML directory)
  - Fail closed: missing module, invalid export, or `..` / absolute path fails validate/run before any step
  - Embedded `$schema` map (0431) includes the new field so validate and run stay aligned
  - Surface docs: `docs/04_DESIGN.md`, `sp-spur-cli` workflow extension reference, bundled `apps/cli/schemas/*-workflow.schema.json`
  - Catalog bump of `@gobing-ai/ts-dual-workflow-engine` once ts-libs C1 ships the schema
- Out:
  - Authoring the engine schema (ts-libs C1)
  - New Spur builtin kinds (`agent.run` etc. stay)
  - `kk` product-plugin discovery
  - Restoring `@gobing-ai/spur-plugin-sdk` / PluginLoader

## Acceptance Criteria

```gherkin
Feature: Workflow YAML rule-style extensions

  @core
  Scenario: R1 — A listed action module is registered for the same file
    Given a workflow YAML lists extensions.actions: ["./exts/audit.ts"]
    And that module default-exports { name, actions: [{ kind: "audit-log", execute }] }
    When spur workflow run executes a step with kind audit-log
    Then the host runs the extension action

  @core
  Scenario: R2 — A listed guard module is registered for the same file
    Given a workflow YAML lists extensions.guards: ["./exts/flag.ts"]
    And that module default-exports { name, guards: [{ kind: "feature-flag", evaluate }] }
    When a transition guard has kind feature-flag
    Then the host evaluates the extension guard

  @core
  Scenario: R3 — validate and run fail closed on a bad extension
    Given extensions.actions names a missing file or a module without actions[]
    When spur workflow validate or run is invoked
    Then the command fails before any workflow step
    And the error names the path and the reason

  @core
  Scenario: R4 — dry-run and continue use the same loaded host
    Given a workflow with a custom guard listed under extensions.guards
    When spur workflow run --dry-run or spur workflow continue runs
    Then the extension guard is registered and evaluated

  @edge
  Scenario: R5 — Absolute and parent-traversal paths are rejected
    Given an extensions entry that is absolute or contains ..
    When validate or run is invoked
    Then the command fails and no import is attempted

  @edge
  Scenario: R6 — Surface docs land with the code
    Given the implementing commit
    When 04_DESIGN.md and the workflow extension skill reference are read
    Then they document extensions.actions and extensions.guards
```
