# H51: Batch execution reliability guardrails

## Goal
Make Spur batch execution predictably efficient and truthful by encoding the guardrails discovered
during J4 delivery into the competencies and pipeline surfaces that own retry behavior, task-section
formats, test output, lifecycle transitions, and debugging order.
## Scope
**In scope:**

- Stop identical failing-test loops until source, hypothesis, and edit evidence exists.
- Make task L3 formats and lifecycle guards discoverable before the first write.
- Keep test execution focused and compact while returning the real runner status.
- Batch coherent task-section writes before validation.
- Prefer causal source inspection over unrelated git-state investigation.
- Lock the guidance to source-backed structural regression tests.

**Out of scope:**

- J4 Board UI behavior and observability data-plane implementation.
- A stateful hook that counts repeated shell commands across tool calls.
- Replacing deterministic Spur lifecycle, task-check, or verdict gates.
## Acceptance Criteria
```gherkin
Feature: Batch execution reliability guardrails

  @core
  Scenario: R1 — AC1. Repeated identical test failures trigger source inspection, a falsifiable hypothesis, and an edit before another retry.
    Given a focused test command repeats the same failure signature
    When an agent considers another retry
    Then it inspects the failing assertion and source
    And states a falsifiable hypothesis
    And makes a relevant source or test edit before retrying

  @core
  Scenario: R2 — AC2. The task-section reference exposes the real lifecycle graph, citation shape, review table, verdict schema, and canonical section names.
    Given an agent must author task completion sections
    When it reads the task-section reference
    Then the lifecycle graph and guarded transitions are explicit
    And the citation, review, verdict, and canonical-section formats are explicit

  @core
  Scenario: R3 — AC3. Test guidance favors focused execution and compact output while preserving the real exit status.
    Given a test command can produce verbose output
    When an agent runs or filters it
    Then it selects the narrowest useful test
    And keeps routine output compact
    And returns the test runner's real exit status

  @core
  Scenario: R4 — AC4. Pipeline guidance batches Solution, Testing, and Review before the first task check.
    Given an in-session operation owns multiple pipeline sections
    When it prepares the first validation
    Then complete Solution, Testing, and Review bodies are staged before the first task check
    And one coherent write batch is checked afterward

  @core
  Scenario: R5 — AC5. The workflow source documents valid task transitions and the guards on `wip -> testing` and `testing -> done`.
    Given the task pipeline is inspected
    When an agent reads its lifecycle comments
    Then valid and invalid task transitions are explicit
    And both guarded terminal-path transitions name their checks

  @core
  Scenario: R6 — AC6. Debugging guidance prioritizes the failing test and source over unrelated git state.
    Given a failing test has a local assertion and source path
    When an agent begins root-cause analysis
    Then it inspects the assertion, fixture, module, and caller first
    And unrelated stashes, branches, and diffs are excluded without causal evidence
```
