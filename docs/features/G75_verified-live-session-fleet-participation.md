# G75: Verified live-session fleet participation

## Goal

Let cooperating live Codex, Claude Code and Pi sessions contribute reliable warm fleet capacity through verified declared-member occupancy, preserving human control, durable task outcomes and the existing explicit guest workflow.

## Scope

- In: exact session/process/project identity; working-time guest leases; portable join/pull/reply adapters; optional attested binding to declared members; ready/busy human arbitration; G74 task-turn receipts; fenced detach/recovery; combined performance evidence.
- In: incremental guest hardening that is useful before automatic member binding; existing guest defaults remain explicit and message-only.
- Out: arbitrary PID takeover, terminal injection, replacing human sessions, unverified stage capabilities, new public nouns or verbs, remote fleet infrastructure and duplicate messaging transports.
- Deferred: Grok Build and Antigravity CLI native attachment until exact binary and mode-specific probes establish supported channels; portable cooperative pull remains the baseline.

## Acceptance Criteria

```gherkin

  @core
  Scenario: R1 — A live session keeps exact identity and its lease throughout active work
    # covers: I1, I3, I5, I8

    When the session performs a 90-second job without another inbox wait
    Then independent renewal keeps its session, project and generation binding valid
    And process death, PID reuse or explicit leave cannot transfer that identity to an unrelated process

  @core
  Scenario: R2 — Codex Claude Code and Pi participate through portable inbox adapters
    # covers: I1, I3, I4, I6
    Given one cooperating Codex, Claude Code and Pi session with exact host and mode provenance
    When each joins, waits for a bounded inbox request, performs the work and replies with hooks absent
    Then all three deliver correlated results through the durable inbox
    And an unsupported native wake channel remains an explicit pull-only capability

  @core
  Scenario: R3 — A capable live session binds one declared member without changing guest defaults
    # covers: I3, I5, I6
    Given an idle declared member and a cooperating session with matching project, executor and required capabilities
    When the session requests that member while a competing or mismatched session also attempts to bind
    Then exactly one fenced occupant binds and mismatched capabilities or identity are refused
    And ordinary guests remain concrete-address message participants excluded from automatic role selection

  @core
  Scenario: R4 — Human work retains session ownership until an explicit safe yield
    # covers: I3, I5, I6
    Given a bound session performing human work or waiting for an operator answer
    When a fleet task becomes eligible or the operator requests drain and detach
    Then no fleet turn is injected into the busy human turn and readiness changes only at a safe yield
    And detach stops new assignment, preserves uncertain active work and never kills the human-owned process

  @core
  Scenario: R5 — Attached stages produce the same validated receipts as supervised stages
    # covers: I3, I5, I6
    Given a verified attached occupant and a keyed stage using the G74 execution contract
    When the stage completes, loses its connection or reports a late result after lease transfer
    Then only current correlated completion with valid artifacts can produce success
    And uncertain writing work is reconciled before replacement and a delivered message alone cannot complete the stage

  @core
  Scenario: R6 — A combined fleet receipt distinguishes participation gains from convenience
    # covers: I1, I4, I5, I6, I8
    Given identical first-batch workloads on attached-ready, supervised-cold and supervised-warm workers
    When the repeatable combined comparison includes busy waits, attach overhead and failures
    Then the receipt reports p50 and p95 completion, useful throughput and completion rate with quality and cost guardrails
    And Grok Build and Antigravity CLI are recorded as second-batch probes and no unsupported attachment is counted as a performance gain
```
