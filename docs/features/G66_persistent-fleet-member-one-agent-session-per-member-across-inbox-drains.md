# G66: Persistent fleet member: one agent session per member across inbox drains

## Goal

A fleet member keeps one coding-agent session across inbox drains so it remembers its prior work, using the warmest mode its agent supports (persistent stdin, resume by id, or one-shot as last resort), and a restart starts a fresh session deliberately rather than by accident.

## Scope

- In:
  - **Per-member session state.** `spur agent loop` keeps the member's session id/dir for the life of the loop process and passes it to each drained run.
  - **Mode selection from the capability matrix (B8).** `persistentStdin` → one long-lived agent process fed through stdin (the runner's `TeamAgentProcess`); else `resumeById` → one-shot run resuming the session; else one-shot fresh with one warning per member lifetime.
  - **Deliberate reset.** Supervisor restart, `spur agent stop` + `start`, and a bounded number of consecutive failed drains reset the session; the run record names the reset reason.
  - **Observability.** The fleet snapshot and process entry carry the session mode and current session id; E6 maps each drained run to its session.
  - **Delivery safety.** The 0834 reconcile-before-first-drain and settled-message guarantees hold unchanged under a resumed session.
- Out:
  - Fleet strategy, orchestrator binding, and the rest/GTD runtime.
  - PTY or terminal-driven members.
  - Board UI beyond surfacing the existing snapshot fields.

## Acceptance Criteria

```gherkin
Feature: Persistent fleet member

  @core
  Scenario: R1 — Consecutive drains resume the member's session
    Given a fleet member whose agent can resume a session by id
    When two messages are drained one after the other
    Then the second run resumes the session created by the first
    And both run records carry the same session id

  @core
  Scenario: R2 — A persistent-stdin agent runs as one long-lived process
    Given a fleet member whose agent declares persistentStdin
    When the member starts and messages are drained
    Then one agent process stays alive across drains
    And each drained message is injected through its stdin

  @core
  Scenario: R3 — An agent without session support falls back to one-shot with one warning
    Given a fleet member whose agent declares neither persistentStdin nor resumeById
    When messages are drained
    Then each drain runs a fresh one-shot process
    And exactly one warning per member lifetime names the missing capability

  @core
  Scenario: R4 — A restart starts a fresh session deliberately
    Given a fleet member with an active session
    When the supervisor restarts it or the operator stops and starts it
    Then the next drain starts a new session
    And the run record names restart as the reset reason

  @core
  Scenario: R5 — Session mode and id are observable
    Given a running fleet member
    When the fleet snapshot or the process entry is read
    Then it carries the session mode and the current session id

  @core
  Scenario: R6 — Resumed sessions never redeliver settled messages
    Given a member that resumed its session after a drain
    When the next drain runs
    Then messages settled by the previous drain are not delivered again
    And unfinished requests are reconciled before the drain as before

  @edge
  Scenario: R7 — Repeated failed drains reset a poisoned session
    Given a member whose consecutive drains fail up to the bounded limit
    When the limit is reached
    Then the session is reset before the next drain
    And the reset is logged with the failure count as the reason
```
