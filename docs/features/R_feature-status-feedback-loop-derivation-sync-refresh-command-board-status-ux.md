# R: Feature status feedback loop: derivation sync, refresh command, Board status UX

## Goal
Close the task→feature status feedback loop so a feature's status always reflects its tasks' reality — and make that status visible and filterable in the Spur Board Features module.

### What reaching the end looks like

- A derivation rule maps a feature's linked-task-set state onto legal feature-lifecycle transitions, implemented once (app service) and exposed through the CLI and the (currently stubbed) `POST /features/{id}/sync` Board endpoint.
- After a task verifies PASS, the linked feature's status is refreshed through that rule; when the task has no `feature_id`, the operator gets a suggest/confirm/skip prompt (explicit skip allowed).
- A slash command refreshes feature status by feature id, task WBS, or batch sweep — the daily driver until the hooks make it redundant.
- The Board Features tree shows a status icon per node and a status-filter popup in the panel header (before `+`), so incomplete features are findable in seconds.
- The drifted corpus (170+ done tasks under mostly backlog/active features) is backfilled once, with operator confirmation.
## Scope
- Derivation rules + sync implementation seam: `packages/app` feature-service, `spur feature` CLI surface, un-stub `apps/server` sync handler.
- plugin sp: post-verify refresh hook point(s), refresh command surface, missing-`feature_id` suggest/confirm/skip (reuse `feature-link-helper`).
- Board Features module: per-node status icon; header status-filter popup menu.
- One-time live-corpus backfill with operator confirmation.

## Notes
### Existing machinery (surveyed 2026-07-24 — the map's low-res terrain)

- Feature statuses: `backlog → active → verifying → blocked → done → cancelled` (`packages/domain/src/planning/schema.ts:23`). `verifying` is the L4 AC-traceability gate; one active goal corpus-wide.
- CLI: `spur feature update <id> [status]`, `advance <id> --to <s>` (legal forward hops), `refresh` (rebuilds INDEX/tree/`## Tasks` — NOT status derivation), `check`.
- Board sync seam exists but is STUBBED: `POST /features/{id}/sync` with `direction: pull|push` (`packages/contracts/src/feature.ts:304`); handler returns `affectedTasks: 0` with "full implementation deferred" (`apps/server/src/modules/feature/handlers.ts:121`).
- `feature-link-helper` (`plugins/sp/skills/spur-dev/references/feature-link-helper.md`) ALREADY implements: list candidates → LLM-judge match → propose → confirm → apply link (`spur task update <wbs> --feature <id>`), plus batch-sweep mode for orphan tasks (per-orphan confirm/skip/override). The missing-feature-id UX and the batch-scan scenario reuse this — do not reinvent.
- `wrapup-pipeline.yaml` has a `feature-transition` step: `spur feature advance ${vars.feature}` — only when `vars.feature` is explicitly passed, and unconditional (not derived from task states).
- Board: `FeatureTree.tsx` already renders a text `StatusBadge` per node (line 79/103); `FeaturesShell.tsx` header has only the `+` button; SSE `feature.*` events keep tree/detail live.
- Task check reads feature status (`packages/app/src/services/task-check.ts:822`).
