# E2: Session-forensics extension of the history plane: forensic primitives, derived-variable analyze, multi-mode report, rewritten find-issue

## Goal
### Destination

One or more **implementation-ready task files** that specify how `spur history` gains omp's
session-forensics capability — forensic primitives retained at import, derived variables computed by
`analyze`, a `--mode`-selected report renderer, and a `/sp:dev-find-issue` rewritten to consume them.

The map closes when those task files exist and pass `spur task check`, not when the code lands.
Implementation is a downstream effort against the specs this map produces.

### Why this is a map and not a spec

Feature **E1** already shipped the history data plane (`import` across 10 sources with
full/incremental/force-file modes and `--source all` fan-out; `analyze` with the Q1–Q10 forensic query
set; `report` as a pure artifact renderer; `daily` as the scheduled loop). The question is not "build a
history plane" — it is **which parts of omp's forensics methodology the existing plane can already
carry, and which require schema, mapper, or contract changes**.

That answer is not knowable from reading the request. One structural gap is already visible without
investigating: `history_tool_call` stores `args_digest` (a hash), not the arguments
(`~/xprojects/ts-libs/packages/llm-jsonl-importer/src/schema-sql.ts:120`). omp's phase detection reads
**todo-event contents** to name phases, so the single most distinctive primitive in the sample report
cannot be computed from the current schema at all. How many more gaps like that exist, across ten
sources, is exactly what the frontier tickets are for.
## Scope
### In

- `spur history import` — retaining whatever forensic payload the primitives need, and the per-source
  mapper work that makes ten agents produce one comparable shape.
- `spur history analyze` — the derived-variable layer (phases, time decomposition, bottleneck ranking,
  issue candidates) on top of today's Q1–Q10 set.
- `spur history report` — `--mode` selection bound to a renderer, forensics being the first new mode.
- `spur history daily` — the `--mode` wiring only; the verb itself stays (see Decisions so far).
- `plugins/sp/commands/dev-find-issue.md` + `sp:issue-finding` — the rewrite that consumes the above.

### Out

See `### Out of scope` under `## Notes`.

### Open questions

Operator judgment only — never tasks. Resolve in conversation, then move to `### Decisions so far`.

1. **How much tool-call payload should import retain?** Full args, a digest plus a per-tool allowlist
   (e.g. todo-writing tools only), or structured extraction at import time. This is a
   privacy-and-DB-growth ruling, not a technical finding: session logs carry file contents, prompts,
   and occasionally secrets, and `history_tool_call` is currently digest-only by construction.
   *Blocks:* the import half of the specs. *Wait for:* the coverage matrix, which will say what each
   primitive actually needs.
2. **Does `/sp:dev-find-issue` still write a task file?** Today it ends by generating a structured task
   file of proposed fixes. If the CLI produces the report, the command could become report-only with
   task creation behind a flag, or keep the task file as its primary output. *Blocks:* the command
   rewrite spec. *Wait for:* the report-mode spike, which will show how much of the current command
   body survives.

### Decisions so far

- **`spur history daily` stays and gains `--mode`** (operator, 2026-08-09) — it already exists, is the
  scheduled loop, and owns per-source failure isolation, checkpoint self-heal, and 90-day pruning.
  Re-creating that composition in a shell script is churn. It gains report-mode wiring; nothing else.
- **Report modes are built-in named renderers, not file templates** (operator, 2026-08-09) —
  `report --mode spend|forensics|…` resolves to a TS renderer over the artifact, like today's
  `renderReport`. No template engine, no variable-binding contract, no new config surface. File
  templates are deferred until a second author needs one.
- **The destination is implementation-ready task files, not landed code** (operator, 2026-08-09) — the
  map produces specs; implementation is a downstream effort.

### Not yet specified

- Whether forensic primitives are **materialized at import** (columns/tables written once) or
  **computed at query time** in `analyze`. Hangs on the coverage matrix and on the payload-retention
  ruling — materializing is only possible for what import retains.
- Whether **phase detection generalizes past todo-bearing agents**. omp and Claude Code write todos;
  codex, gemini, opencode, antigravity, openclaw, grok may not. If a source has no todo signal, phases
  need a fallback (the methodology names alternatives in §"Alternative Phase Detection Methods") or the
  forensics mode degrades for that source. Sharpens once the coverage matrix lands.
- **Artifact schema versioning.** `HISTORY_ARTIFACT_SCHEMA_VERSION` is 1 and `assertArtifactVersion`
  rejects mismatches. Adding derived variables changes the artifact shape; whether that is a v2 with a
  migration, an additive optional block, or a side-car artifact is unclear until the derived-variable
  mechanism is chosen.
- **Cost-model currency.** `MODEL_PRICING` (`packages/domain/src/analytics/models.ts`) falls back to
  `UNKNOWN_MODEL_PRICING` at $3/$15 per 1M. How many models in the real logs hit that fallback, and
  whether a stale price makes the forensics report's cost ranking wrong, is unmeasured.
- **The command / skill split after the rewrite.** `/sp:dev-find-issue` and `sp:issue-finding` currently
  divide the work one way; when the CLI does the extraction, which of them shrinks — and whether the
  skill survives at all — is not yet answerable.
- **Retention pressure.** If import starts keeping more payload, the DB grows without bound; `daily`
  prunes reports but not history rows. Sharpens only if the retention ruling says "retain more".

### Out of scope

- **The E1 run-cost regression.** `packages/domain/src/analytics/run-cost.ts:103` (`loadAllEtlPayloads`)
  reads only `history_etl_*`, which no longer receives rows for the six converted sources
  (claude, codex, pi, omp, grok, agy), so workflow run-cost attribution is blind to all of them —
  including the default agent. Real, unowned, and E1's cost-attribution surface, not this map's report
  plane. Ruled out by the operator, 2026-08-09.
- **File-authored report templates.** Deferred by the report-mode decision above; returns only if a
  second template author appears.
- **Porting the Python reference implementation.** `docs/session-forensics-report-generation.md`
  §"Complete Python Reference Implementation" is read as a methodology spec, not transliterated.
- **Rebuilding `daily` as a shell script.** Ruled out by the `daily` decision above.
- **A new `spur history forensics` verb.** The methodology doc proposes one (§"Proposed Enhancement");
  this map instead routes forensics through `report --mode forensics`, keeping the noun's verb count
  flat.
