# P: pipeline-dispatch-reliability

## Goal

Bound the three dispatch-reliability gaps left open by the D61 batch post-mortem (0777 findings F5, F7, F10): model-selection semantics for `implementAgent=auto`, watcher report freshness, and test-fix mutation policy.

## Scope

- In:
  - **F5 —** Document (and let the operator decide) the resolution order of `implementAgent=auto`: today it follows capability attestation and ignores the operator's interactive session model; no silent behavior change.
  - **F7 —** Watcher/child report acceptance verifies run identity freshness (report run-id matches dispatched id; log mtime ≥ dispatch time); long-lived watch loops get a bounded lifetime or poll-count cap.
  - **F10 —** The test-fix stage's mutation scope is bounded by the task's declared mutation policy; classification-only tasks (mutation policy: none) never receive source-code edits from test-fix — the hop halts with the failure surfaced instead.
- Out: F1 (env marker leak — fixed), F2/F3 (executor doc + L4 evidence — fixed, 0776/809fc0781), F4 (capability preflight warning — implemented with 0777), F6 (implement-hop budget — mitigated in 0773 Design), F8 (duplicate SHAs — resolved at batch merge), F9 (stale scratch — removed with worktree cleanup).

## Acceptance Criteria

```gherkin
Feature: pipeline-dispatch-reliability

  Scenario: Auto resolution semantics are documented
    Given implementAgent=auto
    When the docs describe model selection
    Then the resolution order follows capability attestation, the interactive session model exclusion is stated, and any change is operator-approved

    Given a task whose mutation policy is none
    When its test gate fails and the test-fix hop runs
    Then the hop halts with the failure surfaced and performs no source-code edits
```
