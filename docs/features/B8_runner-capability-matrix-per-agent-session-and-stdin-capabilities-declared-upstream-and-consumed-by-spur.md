# B8: Runner capability matrix: per-agent session and stdin capabilities declared upstream and consumed by Spur

## Goal

Each coding-agent shim in `@gobing-ai/ts-ai-runner` declares what it can do — resume by id, session directory, persistent stdin, structured output — and Spur reads that declaration instead of hard-coding agent names, so dispatch, affinity and fleet modes pick the warmest supported path per agent and fail loudly where a capability is absent.

## Scope

- In:
  - **Upstream declaration.** An exported `AgentCapabilities` record per `AgentName` (`resumeById`, `sessionDir`, `persistentStdin`, `structuredOutput`) plus the agent CLI version it was verified against, and a `getAgentCapabilities(agent)` accessor.
  - **Known gaps closed where the CLI allows.** codex: resume an `exec` session if the installed codex CLI supports it, otherwise declare `resumeById: false` with a recorded reason. claude: `resumeById: true`, `sessionDir: false`, session id discovered from output. gemini: `resumeById: false` (`-r latest` is not by-id).
  - **Spur consumption.** `agent-run.ts` affinity branches, `agent doctor --json`, and capability attestation read the record; a stage may declare `requiresCapabilities: [resumeById]` and gets a contract-violation outcome before spawn when unmet.
  - **Release.** ts-ai-runner release and `bun update` recorded in the workspace catalog.
- Out:
  - New agents or new shim argv beyond session/stdin flags.
  - PTY or terminal-driven modes.
  - Spur-side session pinning (B7) and fleet loop changes (G66).

    Given a workflow stage declaring requiresCapabilities resumeById

  Scenario: R7 — A stale capability declaration is surfaced
    Given a capability record verified against one agent CLI version

    And routing is not changed by the warning

    Given the runner change is published
    When Spur consumes it
