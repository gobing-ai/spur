# Q: AC-verifiable execution: BDD test scaffolds and tunable validation gates

## Goal
Make each task's Acceptance Criteria verifiable at the code level, and make the four-layer validation gate's severities tunable per project.

Today AC is machine-parsed into structured Gherkin scenarios (`packages/domain/src/bdd/parser.ts`) and coverage is checked at the spec level (`checkAcCoverage`, task ⊆ feature by title), but there is no link between a scenario and a test — AC coverage is invisible in the test run. Separately, check severities are hardcoded at ~20 call sites with only a global `--strict` boolean, and findings carry no stable identity, so a team cannot tune which rules block a gate.

This feature closes both gaps: generate a visible pending test per AC scenario, and give every finding a stable code plus a config-driven severity override map.
## Scope
**In scope**

- A CLI path that generates one pending/`todo` test stub per AC scenario, reusing the existing `packages/domain/src/bdd` parser — idempotent, non-destructive, outline-aware.
- Stable finding `code`s on every task/feature check finding (extends `CheckFindings`).
- A config-driven severity override map on the existing `tasks` config block (`packages/config/src/index.ts` `tasksConfigSchema`), applied in `summarizeWithStatus` alongside the current `--strict` elevation.

**Out of scope**

- Executable end-to-end test generation (step-definition glue / real assertions) — this feature emits stubs only; humans fill the bodies.
- A new L5 validation layer — deferred; the test⇄AC coverage check, when built, belongs as an L3/L4 rule, not a new tier.
- Changes to the L1–L4 default severities themselves — config only *overrides* by code; code defaults stay in source.
## Acceptance Criteria
```gherkin
Feature: AC-verifiable execution

  @core
  Scenario: One pending test per scenario
    Given a task whose Acceptance Criteria has multiple Gherkin scenarios
    When BDD scaffold generation runs for that task
    Then one pending test is written per scenario, each named for its scenario

  @core
  Scenario: Filled stubs are never clobbered
    Given a previously scaffolded stub whose body an author has filled
    When scaffold generation runs again
    Then the filled body is preserved and only new scenarios are appended

  @edge
  Scenario: Scenario Outline expands per example row
    Given an AC scenario outline with two example rows
    When scaffold generation runs
    Then two pending stubs are written with the row data recorded

  @core
  Scenario: Every finding carries a stable code
    Given a task or feature check produces findings
    When the findings are emitted
    Then each finding carries a stable machine code identifying its rule

  @core
  Scenario: Config overrides a finding severity
    Given a severity override map in the tasks config block
    When a check runs and a finding's code is listed
    Then that finding is emitted at the configured severity

  @edge
  Scenario: Unknown code in config is rejected
    Given a severity override map naming a code that no rule emits
    When the config is validated
    Then loading fails with a clear error naming the unknown code
```
