# K41: Gateway-root multi-project MCP endpoint

## Goal

Serve one MCP endpoint at the gateway root that lists the tools of every local registered project and routes each call to that project's own `spur serve`, so a coding agent configured once can operate any project and any plugin namespace.

## Scope

**In scope**
- Gateway `POST /mcp` with its own bearer token (`server.gateway.mcp.authEnv`, env `SPUR_GATEWAY_MCP_AUTH_ENV`); `mcp` becomes a reserved prefix segment, independent of each project's `server.mcp.authEnv`.
- tools/list aggregation over local entries, computed from each project's files (plugin-manifest namespace + exposed workflows) so listing never starts a project: `sp_*` built-ins listed once with a required `project` argument; namespaced workflow tools listed per owning project.
- tools/call routing to `/<prefix>/mcp` of the resolved project, starting it on demand through `startRegisteredProject`, forwarding the project's own token from the gateway environment.
- Remote registry entries excluded per ADR-151 and reported in discover diagnostics with the remedy.

**Out of scope**
- Proxying to remote hosts (ADR-151; a separate decision).
- Gateway-side state, caches or databases.
- Agent configuration rollout (the hub feature owns it).

## Acceptance Criteria

```gherkin
Feature: Gateway-root multi-project MCP endpoint

  @core
  Scenario: R1 — Gateway MCP has its own bearer token
    Given the gateway runs with server.gateway.mcp.authEnv set
    When a request reaches the gateway-root /mcp with a missing, wrong or valid token
    Then it answers 401 with a spur-gateway-mcp realm, 500 fail-closed when the variable is unset, or serves the request

  @core
  Scenario: R2 — tools/list aggregates local projects by namespace
    Given two local projects with different namespaces, each exposing one workflow tool
    When a client lists tools at the gateway root
    Then sp_ built-ins appear once with a required project argument, each namespaced workflow tool appears once, and a namespace claimed by two projects is reported and not routed

  @core
  Scenario: R3 — tools/call routes to the owning project and starts it on demand
    Given a stopped local project registered with the gateway
    When a client calls one of its tools through the gateway root
    Then the gateway starts the project, forwards the call to /<prefix>/mcp with that project token, and returns its result unchanged

  @edge
  Scenario: R4 — Remote entries are excluded with a remedy
    Given a registry containing a remote entry
    When a client calls server/discover at the gateway root
    Then the remote project is absent from tools and named in diagnostics with the reason and remedy

```
