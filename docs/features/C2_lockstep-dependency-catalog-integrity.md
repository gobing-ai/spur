# C2: Lockstep dependency catalog integrity

## Goal

Prevent partial lockstep catalog updates from reaching feature acceptance by reporting inconsistent @gobing-ai/ts-* version specifiers before dependency installation is diagnosed through type errors.

## Scope

In: root workspaces.catalog consistency, scripts/commands/dependency-drift-check.ts and its fixtures, the existing feature-scoped dependency-drift-check entrypoint. Out: registry minimum-version policy, automatic dependency upgrades, portable rule evaluators, changes to task-local preset composition.

## Acceptance Criteria

```gherkin
Feature: C2
Scenario: Split pins fail before dependency diagnosis
  Given a temporary manifest with eleven matching pins and one divergent ts-rule-engine pin
  When the dependency-drift-check command reads that manifest
  Then it exits nonzero and lists every package and specifier in both groups
  And its diagnostic names catalog consistency rather than an installed-package type error

  Given scripts/commands/dependency-drift-check.test.ts and the root gate scripts

  And an equal catalog still permits existing installed-drift detection to fail
  And only the existing feature-scoped entrypoint owns the assertion
```
