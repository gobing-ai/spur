# H21: Cross-platform hook core: one ledger and session implementation for Claude Code and Pi

## Goal

One platform-neutral implementation of the indexed-context ledger and session lifecycle serves both Claude Code hooks (`context-post-tool`, `context-session-start`, `context-session-stop`) and the Pi extension (`plugins/sp/hooks/pi/guard-extension.ts`). Pi rows and `.session.json` become indistinguishable from Claude ones, so the token-ledger reader, session rollups, nested-run session reuse and context-freshness stamping behave the same on every host. Today Pi re-implements a thinner copy that has already drifted three times (raw secrets in summaries, `timestamp` vs `ts`, `path` vs `file`; fixed in 2d430c7f5 / 3571e710a).

## Scope

- In: extract/export session-start and session-stop cores from `context-session-start.ts` / `context-session-stop.ts`; make `recordToolUseEvent` (`context-post-tool.ts`) accept Pi's lowercase tool names; delete Pi's private `initSession` / `cleanupSession` / `readSessionId` / `generateSessionId` / `appendToLedger` / `summarizeToolEvent` and route Pi events through the shared cores; a Pi-vs-Claude parity test matrix.
- Out: changing the ledger row schema or `.session.json` schema beyond what Claude already writes; the token-ledger reader (`packages/app/src/services/token-ledger-service.ts`); guard logic (write-guard / careful-guard are already shared via `task-file-policy.ts` / `destructive-policy.ts`); other hosts (omp, Codex, …); wiring `careful-guard` into Claude `hooks.json`.

## Acceptance Criteria

```gherkin
Feature: Cross-platform hook core: one ledger and session implementation for Claude Code and Pi

  Scenario: R1 — Pi tool rows match Claude tool rows
    Given the same Read, Write, Edit, Bash, Grep and Glob events delivered once via the Claude hook payload and once via the Pi tool_result event
    When each is recorded to token-ledger.jsonl
    Then the two rows are equal on ts-independent fields (session, type, file, summary, tokens, action, agent, model)

  Scenario: R2 — Pi session file uses the Claude schema
    Given a Pi session_start event with no .session.json present
    When the session is initialised
    Then .session.json carries "session" (not "session_id") and "started", and one session_start ledger row with contextFreshness is appended

  Scenario: R3 — Pi reuses an in-flight session like Claude
    Given a live .session.json and SPUR_RUN_ID set in the environment
    When Pi fires session_start again
    Then no new session is minted and no ledger row is written

  Scenario: R4 — Pi shutdown rolls up like Claude
    Given a Pi session with recorded read and write rows
    When Pi fires session_shutdown
    Then one session_end row with totals {reads, writes, tokens} is appended and .session.json is removed

  Scenario: R5 — Pi has no private ledger or session implementation
    Given the Pi extension source
    When it is inspected
    Then it defines no initSession, cleanupSession, readSessionId, generateSessionId, appendToLedger or summarizeToolEvent and imports the shared cores instead
```
