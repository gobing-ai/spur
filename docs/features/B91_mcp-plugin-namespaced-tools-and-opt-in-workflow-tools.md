# B91: MCP plugin-namespaced tools and opt-in workflow tools

## Goal

Name every MCP tool `<namespace>_<verb>`, where the namespace is the plugin prefix that provides it (`sp` for Spur, `cc` for superskill, `kk` for knowledge-kit), and let any project expose chosen workflows as MCP tools under its own namespace, so agents loading many MCP servers see collision-free, source-identifying tool names without a runtime registration API.

## Scope

**In scope**
- Rename the five built-in harness tools to `sp_task_show`, `sp_task_list`, `sp_workflow_status`, `sp_workflow_run`, `sp_workflow_continue` (breaking; amends the frozen names of task 1372 R2 and ADR-152).
- Project namespace resolution: `server.mcp.namespace` (env `SPUR_MCP_NAMESPACE`), else the `name` of the single depth-1 `plugins/<name>/plugin.json`, else none; reported by `server/discover`.
- Workflow opt-in: a workflow YAML declaring `metadata: { mcp: { expose: true } }` (a behavior-free `metadata` key added to the workflow engine schema) becomes tool `<namespace>_<workflow-name>` described by the workflow `description` with an input schema derived from its declared vars; calls run through `WorkflowService.run`.
- `spur workflow validate` refuses an exposed workflow whose tool name collides with a built-in or another exposed workflow, or that is exposed in a project with no namespace.

**Out of scope**
- Runtime tool registration APIs or plugin-supplied executable code.
- Exposing every workflow by default (exposure is explicit opt-in).
- Cross-project aggregation (the gateway-root MCP feature owns it).
- Backward-compatible aliases for the old unprefixed tool names.

```gherkin
  Scenario: R1 — Built-in harness tools carry the sp namespace
    Given an enabled MCP endpoint
    When a client lists tools

  Scenario: R2 — Project namespace resolves from config then plugin manifest
    Given a project with server.mcp.namespace set, one with a single plugins/<name>/plugin.json, and one with neither
    When server/discover is called on each
    Then the namespace is the config value, the plugin manifest name, or absent respectively, and an invalid namespace fails config load

  @core
  Scenario: R3 — An opted-in workflow becomes a namespaced MCP tool
    Given a project with namespace cc and a workflow declaring metadata.mcp.expose true with declared vars
    When a client lists tools and calls cc_<workflow>
    Then the tool appears with an input schema derived from the vars, the call runs through WorkflowService.run, and workflows without mcp.expose are not listed

  @edge
  Scenario: R4 — Tool-name collisions are refused at validate time
    Given an exposed workflow whose derived tool name equals a built-in or another exposed workflow, or a project without a namespace
    When spur workflow validate runs
    Then validation fails naming the colliding tool and the remedy

```

## Notes

Tool-name grammar: `[a-z0-9_]`; `:` is assumed not to be valid in MCP tool names (verify against the MCP 2026-07-28 spec in task 1379). The registry field `prefix` already means the URL path prefix (docs/design/project-gateway.md §3) — the new key is `server.mcp.namespace`, fed by env `SPUR_MCP_NAMESPACE` (the server config surface is env-scoped), so no `spur projects` flag change is needed.

Phase 1 of the protocol-surfaces roadmap (2026-11-17 planning session).
