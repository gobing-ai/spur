# J8: Pairing evidence: agent×model×role measurement and ladder recommendation from the history plane

## Goal
Turn the operator's model↔agent pairing philosophy (native pairs at capable rungs; portable
models via omp/pi at cheap/standard) into a maintained, evidence-backed table: aggregate the
history data plane per (agent, model, role) — dispatches, success/escalation rates by signal,
cost, duration, verdict pass rate — and render a ranked pairing report that diffs the measured
ranking against the configured executor ladder and proposes concrete reorderings. The harness
measures and recommends; the operator applies. Layers 1–2 of the 2026-08-16 proposal only.
## Scope
In:

- A pairing aggregation over the existing history plane (sessions, run↔session mapping, routing
  attribution — the same rows `roleTokenSummary` reads in `packages/domain/src/analytics/`),
  producing per-(agent, model, role) stats inside the versioned `spur history analyze` artifact.
- A new registry-resolved report mode (e.g. `spur history report --mode pairings`) that renders
  the ranked table from the artifact — a pure renderer that never opens the database, matching
  the report contract (0564 R3).
- A ladder-diff section in that mode: compare measured ranking vs `.spur/config.yaml` executor
  order per tier and print concrete promote/demote suggestions with their evidence.
- Test coverage over fixture artifacts + real-data dogfood of both analyze and report.

Out:

- Shadow/A-B routing experiments (Layer 3) — deferred until dispatch volume justifies it.
- Any automatic config rewrite — recommendation only; the operator edits YAML.
- J6's own query API work (this feature consumes the attribution rows J6 surfaces; the
  aggregation inputs already exist, so J8 does not hard-block on J6).
- New CLI nouns/verbs, new import sources, or ETL changes.
## Acceptance Criteria

  @core
  Scenario: R1 — The analyze artifact carries per-pairing stats
    Given a history database with attributed runs (agent, model, role recorded)

    Then the versioned artifact contains a pairings section keyed by (agent, model, role)
    And each entry reports dispatch count, success rate, escalation rate by signal, cost, and duration

  @core
  Scenario: R2 — The pairings report mode renders the ranked table without the database
    Given an analyze artifact containing a pairings section
    When `spur history report --mode pairings` runs against it
    Then it renders pairings ranked per role by the documented ordering (success rate, then escalation rate, then cost)
    And it never opens the database (pure renderer of the artifact)
    And an unknown mode name still fails loudly (registry-resolved)

  @core
  Scenario: R3 — The ladder diff proposes concrete reorderings with evidence
    Given an analyze artifact carrying a ladder snapshot embedded from the project config
    When the pairings report renders
    Then a ladder-diff section names each rung whose measured ranking disagrees with its snapshotted position
    And each suggestion cites the underlying numbers (dispatch count, rates, cost)
    And a rung with fewer than the documented minimum dispatches is marked insufficient-evidence, never suggested

  @deprecated
  Scenario: R4 — The artifact schema version bumps and old artifacts degrade gracefully
    Given an artifact written before the pairings section existed
    When the pairings report renders it
    Then it reports the section as unavailable (naming the analyze version needed) instead of failing or fabricating rows

  @core
  Scenario: R6 — The pairings section is additive and old artifacts degrade gracefully
    Given the artifact contract is additive-only (HISTORY_ARTIFACT_SCHEMA_VERSION stays 1)
    When the pairing aggregation lands
    Then `pairings` and `ladderSnapshot` are optional additive fields and the version is unchanged
    And a pre-pairings artifact renders an explicit "section unavailable" notice (absence-as-unknown, the SessionStat.sessionState precedent) instead of failing or fabricating rows

  @edge
  Scenario: R5 — Real-data dogfood on this monorepo
    Given the real history DB (post-0567 import surface)
