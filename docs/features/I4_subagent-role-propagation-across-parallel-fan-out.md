# I4: Subagent role propagation across parallel fan-out

## Goal
A subagent dispatched during parallel fan-out carries **its own** role, so routing and attribution
stay correct when one agent dispatches several others.

Feature B2's fog names this as unexplored: *"`sp:parallel-execution` dispatches several subagents at
once. Whether each carries its own intention, or inherits the parent's, is unexplored."* Once
`--agent <role>` ships (batch 1) and role attribution is recorded (batch 2, task 0545), an unanswered
propagation rule means a planner fanning out four implementation subagents either routes all four to
`capable-2` — paying planner rates for coder work, the exact waste tiers exist to prevent — or
attributes their consumption to the wrong role.
## Scope
- In:
    - The propagation rule: a dispatched subagent declares its own role; absent a declaration it
      inherits the dispatching agent's.
    - Wiring that rule through `sp:parallel-execution`'s dispatch surface and any other fan-out path
      that shells out to `spur agent run`.
    - Making the effective role visible per dispatched subagent, so a wrong inheritance is
      observable rather than silent.
- Out:
    - The role vocabulary and the `--agent` selector — feature B2, batch 1.
    - Recording or aggregating attribution — feature J6, batch 2. This feature makes the value
      correct; J6 records it.
    - Changing how fan-out chooses concurrency, or the fan-out patterns themselves.
    - Nested fan-out beyond one level. If a dispatched subagent itself fans out, the same rule
      applies recursively by construction; no special handling is in scope until a case appears.

## Notes
### The default is inherit, and that is a deliberate choice

Declared-wins-over-inherited is the rule because the alternative fails in the expensive direction: a
planner fanning out four implementation subagents would run all four at `capable-2`, paying planning
rates for coder work — precisely the waste the tier model exists to prevent.

Inheritance rather than "fail if undeclared" is chosen for the same reason the unmapped-role case
warns instead of failing (feature B2, task 0536): a missing declaration is a plausible authoring
omission, and refusing to run is disproportionate. Making the inheritance **visible** (R3) is what
keeps it from being silent.

This is a reversible call. If inherited-by-default turns out to mask more mistakes than it smooths,
the alternative is a warn-on-inherit or a hard requirement, and either is a small change once R3's
visibility exists.

### Sequencing

Needs feature B2's `--agent <role>` (task 0536) to exist before a role can propagate, and pairs
naturally with feature J6 task 0545, which records whatever this feature makes correct.
