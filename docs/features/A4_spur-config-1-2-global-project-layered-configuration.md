# A4: Spur config 1.2: global + project layered configuration

## Goal
**Destination.** `spur` resolves configuration by deep-merging a user-global
`~/.config/spur/config.yaml` **under** the project's `.spur/config.yaml`, so a project config
carries only its delta — and `spur init` stops copying machine-wide assets into every project.

### What reaching the end looks like

- **One schema, two layers.** `spurConfigSchema` validates both files. Every top-level key is
  already optional on both sides, so each file legitimately carries a subset.
- **Deep-merge-then-validate.** Layers parse as raw YAML, merge, and the *merged* result is
  validated exactly once. A partial entry is a legal merge fragment; it is never a legal config.
- **`agent.executors` merges by `name`.** A project overrides one field of a global executor
  without re-pasting the whole list — the duplication that motivated this effort.
- **`config/config.global.yaml`** (repurposed from `config.example.yaml`) is the shipped default
  seeded to `~/.config/spur/config.yaml`, carrying `agent.default`, `agent.executors`,
  `agent.roles`, and `workflows`.
- **`spur init` writes a delta.** It no longer copies `.spur/templates` (project→bundled fallback
  already exists). `.spur/rules` keeps its per-project copy — rules depend on project folder
  structure and are deliberately excluded.
- **Role→tier SSOT moves into config**, superseding ADR-061; code retains a minimal fallback for
  the no-config-file case.
- **`agent.team` stays project-level**, untouched by this effort.
## Scope
- In:
    - `spurConfigSchema` / `apps/cli/schemas/spur-config.schema.json` changes for the `1.2` label
      and the two-layer subset model.
    - `resolveConfigFile` / `loadSpurConfig` in `packages/config/src/loader.ts`: two-file load,
      deep merge, single post-merge validation, cache keying, `SPUR_SKIP_GLOBAL_CONFIG` semantics.
    - Per-key merge strategy for every `spurConfigSchema` key plus the unschema'd `bootstrap` block.
    - `config/config.example.yaml` → `config/config.global.yaml` and its seeded content.
    - `spur init` seeding: which `.spur/` copies survive, which are dropped.
    - Role→tier SSOT inversion into config and the ADR superseding ADR-061.
- Out:
    - `.spur/rules` — stays a per-project copy; rules depend on project folder structure.
    - `agent.team` semantics, team materialization, and the agent-team/workspace question.
    - The broader role-based agent-execution transition this change is meant to unblock.
    - A projects-registry or per-workspace third config layer.

### Open questions

Operator judgment required — never file these as tasks.

1. **Does `version: "1.2"` gate anything mechanically, or is it a label?** Today nothing is keyed on
   `version` (`index.ts:668` says so explicitly). Options: label-only with a warn on `1.1`; a real
   `spur self migrate` step; or a hard load error below `1.2`. Blocks: what A4 ships as its
   compatibility story.
2. **How does a project remove a global executor?** Merge-by-name has no deletion primitive. A
   `disabled: true` field was offered and not taken. Blocks: whether the merge contract is complete
   or knowingly one-way.
3. **Do array-valued path keys (`rules.paths`, `workflows.paths`) concat or replace?** Different
   answer from `agent.executors` is legitimate — these are search paths, not named records.
   Sharpened by the key-by-key inventory ticket; ruled on by the operator afterwards.

### Decisions so far

Operator rulings, 2026-08-23 charting session:

- **One schema, both layers.** The same `spurConfigSchema` validates global and project files; each
  legitimately carries a subset. No partial-schema twin.
- **Deep-merge is automatic and total.** No per-key opt-in; the loader merges the whole tree.
- **`agent.executors` merges by `name`.** Same-named project entry overrides the global entry
  field-by-field; unknown names append.
- **Validation runs once, after merge.** Layers parse as raw YAML; the merged result is validated
  strictly. This keeps executor `agent` required — a fragment is not a config — instead of
  relocating the failure to dispatch time.
- **`config/config.example.yaml` is repurposed as `config/config.global.yaml`.** One shipped
  default, one seeded target, no third artifact to keep in sync.
- **ADR-061 is overturned.** The role→tier SSOT moves into the config file; code keeps a minimal
  hardcoded fallback for the no-config-file case. A new dated ADR supersedes 061.

### Not yet specified

- **Should `bootstrap` join `spurConfigSchema`?** Sharpened by 0639/0640, not closed: `bootstrap` has
  no zod key, so the single post-merge validation does not cover it — it merges as passthrough and is
  validated only by the JSON Schema, per-file. 0641 settled that it stays *project-shaped*; what is
  still open is whether it should be *validated* at all in the merged result. Needs an operator call
  on whether app-layer validation is sufficient.
- **Whether existing projects get a subtraction path.** A `.spur/config.yaml` that duplicates what is
  now global stays correct under merge but stays duplicated. Nothing mechanically subtracts the
  global layer from a project file.
- **What `spur self status` and the Board show** when config comes from two files.
- **Retiring the last `config.example.yaml` traces.** `config/config.example.yaml` is inert on disk
  (zero consumers) and needs one `rm` the sandbox could not perform; `docs/features/B2` and `B3` still
  name it, correctly for their era — whether historical feature records get rewritten on a rename is
  a project-wide docs-hygiene question, not an A4 one.

### Out of scope

- **`.spur/rules`** — keeps its per-project copy. Rules resolve against project folder structure, so
  the global treatment that suits templates and workflows does not transfer. Operator ruling.
- **`agent.team`** — stays a project-level key, explicitly parked as legacy pending the separate
  agent-team/workspace decision. Not touched by this map.
- **The role-based agent-execution transition** this change is meant to unblock. A4 fixes the config
  foundation only; the executor/role rollout is its own effort.
- **A third config layer** (per-workspace, projects-registry-driven, or env-file). Two layers is the
  destination.
