# I14: Grok Bot interop for spur and the sp plugin

## Goal

Let the sp plugin and spur work alongside Grok Bot: sp skills declare their runtime needs so the Bot catalog carries only runnable entries, an opt-in bootstrap installs the spur toolchain on a Bot's cloud computer, and documented recipes let a Bot act as spur's outer loop and let spur workflows notify a Bot routine via webhook — without new public spur nouns or verbs.

Depends on the superskill feature "Grok Bot plugin-native distribution and host probe" for the `requires:` contract and the P0 probe receipt. Evidence: Bot computers have terminal + filesystem and a shared account-wide computer; member-installed packages are removed on recreate while the durable disk is kept (https://docs.x.ai/grok-bot/computers); routines accept webhook triggers with `Authorization: Bearer <key>` (https://docs.x.ai/grok-bot/skills-routines-and-automations).

## Scope

- Annotate sp skills/commands/agents with `requires:` per the superskill contract (≈109 skill files call the `spur` CLI; hook-dependent gates must not be claimed on Bot).
- `sp-bot-bootstrap` skill: idempotent check-then-install of bun + spur/superskill/kk on a Bot computer (check script exits 0 → skip), safe to re-run after recreate; no secrets in the script.
- Recipes (help doc + example workflow using the existing shell step with `curl`): Bot outer loop (GitHub connector clone → `spur task list --json` / next-step triage → issues/PRs) and spur → Bot routine webhook notify (key from environment).
- E2E receipt proving the webhook recipe against a local stub and the bootstrap check/setup idempotency.

**Out of scope:** new public spur nouns/verbs, MCP server, importing Grok Bot history, `spur agent` executor for Grok Bot.

## Acceptance Criteria

```gherkin
Feature: Grok Bot interop for spur and the sp plugin

  Scenario: R1 — sp entities declare runtime requirements (R1)
    Given the sp plugin skills, commands and agents
    When the requires annotations are validated
    Then every entity that shells out to spur, superskill or kk, or relies on hooks or subagents, declares it and a check fails on undeclared use

  Scenario: R2 — Bootstrap is idempotent and secret-free (R2)
    Given a computer with and without the spur toolchain
    When the sp-bot-bootstrap check and setup run twice
    Then the second run is a no-op, the toolchain resolves on PATH and no credential is written to the script or logs

  Scenario: R3 — Webhook notify recipe delivers a run summary (R3)
    Given a workflow using the documented shell curl step and a local webhook stub
    When the workflow completes or fails
    Then the stub receives one authenticated POST with the run summary and a missing key fails the step with an actionable error

  Scenario: R4 — Outer-loop recipe uses only existing surfaces (R4)
    Given the recipe documentation
    When it is reviewed against the spur CLI surface
    Then every command it names exists with --json and no new public noun or verb is introduced
```
