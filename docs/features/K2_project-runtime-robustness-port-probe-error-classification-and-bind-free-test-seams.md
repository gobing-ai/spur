# K2: Project runtime robustness: port-probe error classification and bind-free test seams

## Goal
Keep the project-runtime surface K1 shipped honest in restricted environments, and stop its test
suites from depending on the OS granting a TCP bind.

K1 delivered the `projects.json` registry, auto-assigned ports, and auto-start. Two gaps surfaced
on 2026-08-17 while running the full suite under a bind-denying sandbox:

- **`isPortAvailable` cannot tell "in use" from "not permitted."** It discards the bind error, so
  any environment that denies bind — hardened container, seccomp profile, low-privilege user, agent
  sandbox — makes all 1,000 ports in the band read unavailable and `allocatePort` reports
  *"No available ports in range 3000–3999"*, naming the wrong cause.
- **Twenty tests bind a real port as scaffolding** to reach a branch, rather than controlling the
  seam that decides it. They contend for ports with parallel suites and with a developer's own
  running `spur serve`, and they fail outright wherever bind is denied.

Four further tests bind because the bind **is** the unit under test — including the IPv6 dual-stack
regression `isPortLive`'s docstring ties to a shipped production bug. Those stay real.
## Scope
**In:** `packages/app/src/services/project-registry.ts` port probing (error classification,
capability probe, test seam) and its re-exports; the arrange steps of the seven port-dependent test
files across `packages/app`, `apps/cli`, `apps/server`, `apps/web`.

**Out:** `bun run test-cf` (Vitest's Workers pool binds a real port to host the runtime; no seam
exists). The 3000–3999 band, allocation strategy, and `projects.json` shape — K1's shipped contract.
Any of the 24 tests' assertions. Sandbox configuration itself.
## Acceptance Criteria
```gherkin
Feature: Project runtime robustness

  Scenario: R1 — A denied bind is not reported as a port conflict
    Given an environment that denies binding a TCP port
    When a port is probed
    Then the result is denied rather than in-use
    And port allocation fails naming permission, not band exhaustion

  Scenario: R2 — Port-dependent suites run without binding
    Given tests whose port binding is incidental scaffolding
    When the suite runs in an environment that denies binding
    Then those tests reach their branches through an injected probe
    And they pass without opening a socket

  Scenario: R3 — Tests of the bind itself stay real
    Given tests whose unit under test is the OS bind
    When the environment denies binding
    Then they skip with a printed reason rather than being mocked
    And they execute normally wherever binding is permitted
```
