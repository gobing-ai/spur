# I13: Two-layer plan and progress visibility for dev workflows

## Goal

Every workflow-backed `/sp:dev-*` execution publishes, before any model work, a native todo list that
reads as a plan — two-layer `A`–`Z` / `1`–`9` labels, phases rather than raw FSM states — and keeps it
truthfully synchronized to completion, for single-task and multi-task runs alike.

## Scope

**In scope:**

- Review of the commands, subagents and skill references that drive inline and batch dev runs (`dev-run`, `dev-runall`, `dev-parallel`, `dev-refineall`, `dev-verifyall`, `dev-idea`, `dev-plan`, `sp:super-planner`, `spur-dev` references).
- The two-layer label model, phase grouping of workflow states, cap/fold rules, and the native-todo publish/update contract per host.
- Reuse of the 0814 contract and `step-reporter.ts` helpers; fixing them where they conflict with the model.

**Out of scope:** see `### Out of scope` under Notes.

This feature is a wayfinder map (`wayfinder-map` tag), not a specified deliverable. It carries no Gherkin
acceptance criteria by design: charting records decisions and bounded investigations only. Implementation

## Notes

### Destination

A concrete, operator-approved contract (and graduated implementation tasks) under which every workflow-backed
`/sp:dev-*` run shows a two-layer `A`–`Z`/`1`–`9` native todo plan at planning start and keeps it truthful to the end.

### Charting review findings (2026-10-06)

- **Plan is the raw FSM inventory.** `spur workflow show config/workflows/task-pipeline.yaml --format todo` lists 16 states
  (`precheck … escalate, test-fix, test-recheck, triage, test-fail-triage … failed, cancelled`) as Layer 1; idea-pipeline likewise 16.
  Loop/failure states read as pending work, so the list never looks like a plan or completes cleanly.
- **Label collision.** Bootstrap rows `A Quick readiness … D Comprehensive checking`
  (`plugins/sp/skills/spur-dev/references/cross-cutting.md:251-253`, `inline-pipeline-driver.md:131-134`) reuse the letters the
  workflow inventory then assigns to states (`inline-pipeline-driver.md:179-181`).
- **Cap not enforced.** `columnLabel` (`packages/app/src/workflow/step-reporter.ts:255`) emits `AA, AB…`; `labelChild` has no 9 cap.
- **Tool not wired.** No dev command's `allowed-tools` and no `sp:*` subagent `tools:` list declares a native todo tool
  (`dev-run.md`, `dev-runall.md`, `super-planner.md` frontmatter); the contract is prose only, with no generated payload.
- **Batch has no task layer.** `execution-batch.md` keeps a durable ledger but specifies no per-task native list layout.

Skills to consult: `sp:spur-dev` (inline-pipeline-driver, cross-cutting, execution-batch), `cc:anti-hallucination` for host-tool claims.

### Open questions

- None open at charting. Graduation (after 1101 + 1102) needs operator consent for any public `spur workflow show`
  output change and for the per-state phase assignment the prototype proposes.

### Decisions so far

- Single-task plan = phases + steps: `A` Prepare (`A1` Quick readiness, `A2` Prepare Git, `A3` Publish plan), then `B`.. curated
  workflow phases (e.g. Implement, Test, Review, Verify & record) with digit steps; failure/loop states hidden until entered,
  then inserted as the next digit under their phase. Replaces the separate bootstrap `A–D` rows.
- Multi-task plan = letter per task, digit per phase: `A` Prepare batch, `B`..`Y` one task each (`B 0812 <title>`), `Z` Batch report;
  >24 tasks split into waves, each its own `A`–`Z` plan.
- Cap is hard: fold/wave deterministically, never emit `AA` or `A10`; a definition that cannot fit fails validation at authoring time.

### Not yet specified

- Per-host rendering adapters (nested vs flat tools, status vocabularies) — shape depends on 1101's matrix.
- Who owns the list when work runs in a subagent or parallel worker (parent-only updates vs worker-reported progress via `spur message`).
- Label stability across retry, pause/resume and compaction (re-derivation from run state vs persisted labels).
- Parity of the same labels in the subprocess path (`spur workflow run`, `spur workflow progress`) and the Board.
- Non-workflow skill-only batches (`refineall`, `verifyall`) — what their phases are.

### Out of scope

- Changing FSM semantics, transitions or guards of any pipeline — this is a presentation layer only.
- New public `spur` nouns/verbs without explicit consent; Board UI redesign.
