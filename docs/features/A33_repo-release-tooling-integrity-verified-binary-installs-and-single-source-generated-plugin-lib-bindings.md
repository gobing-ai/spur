# A33: Repo release-tooling integrity: verified binary installs and single-source generated plugin-lib bindings

## Goal

The repo's release tooling under `scripts/` never ships an artifact that differs from what was built, and never keeps two hand-maintained copies of one generated surface. Concretely: `scripts/install.sh` installs a standalone `spur` binary only after verifying its SHA-256 against a checksum file published with the same release, and never destroys a working install on a failed download; and `scripts/commands/bundle-plugin-lib.ts` derives the inline-run bundle's entry exports and its `.d.mts` declarations from one table, so the two cannot drift.

## Scope

- In: `scripts/commands/build-binaries.ts` (emit `dist/cli/SHA256SUMS`), `scripts/install.sh` (verify + atomic replace), install docs that describe the release assets (`README.md`, `apps/cli/README.md`), `scripts/commands/bundle-plugin-lib.ts` inline-run export table and its test, regenerated `plugins/sp/lib/inline-run.generated.d.mts`.
- Out: automating binary release upload in CI (`.github/workflows/` needs explicit operator approval — record as a note, do not edit); signing (minisign/cosign); Windows installer; the artifact-digest and idea-handoff bundles (their declarations are hand-written signatures, not re-exports); `importer-schema-check` auto-remedy (deliberate per 0815 residual 6).

## Acceptance Criteria

```gherkin
  Scenario: R1 — Release build publishes checksums for every binary
    Given build-binaries compiles all four platform targets successfully
    When the build finishes

    Given a release whose SHA256SUMS entry for the platform asset differs from the downloaded bytes
    When scripts/install.sh runs
    Then it exits non-zero naming the checksum mismatch and the previously installed spur is unchanged

  Scenario: R3 — Failed download never destroys a working install
    Given an existing spur binary at the install target and a download that fails mid-transfer
    When scripts/install.sh runs
    Then it exits non-zero and the existing binary is byte-identical to before

  Scenario: R4 — Inline-run bundle exports and declarations come from one table
    Given the inline-run export table in bundle-plugin-lib.ts
    When bundleInlineRunLib runs
    Then every name exported by the generated entry has exactly one declaration in inline-run.generated.d.mts and no declaration exists without an export
```
