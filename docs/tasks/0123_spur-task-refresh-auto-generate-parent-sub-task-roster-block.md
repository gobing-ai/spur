## 0123. spur task refresh: auto-generate parent sub-task roster block

### Background
Follow-on from task 0121 (R5, deferred by scope guard). 0121 delivered the parent↔child roll-up **gate** in `spur task check` — a check that *warns* when a decomposition parent's `## Plan` has no sub-task roster table. This task delivers the **generator** half: a command-driven roster *refresh* for parents, mirroring `spur feature refresh`'s auto-generated `## Tasks` block, so the roster's status column stays current without hand-editing.

Scope: regenerate the parent's `## Plan` sub-task roster table (one row per child task: WBS, title, status) on demand, idempotently. The gate (0121) reads a missing/stale roster; this closes the loop by maintaining it. Reference the existing `feature refresh` auto-block generator (`packages/app/src/services/task-service.ts` byParent index, ~line 710) as the model.
### Acceptance Criteria
```gherkin
Feature: spur task refresh-roster — auto-generate a parent's sub-task roster block

  Scenario: Refresh inserts a roster block into a parent with no existing markers
    Given a parent task with two child tasks and a hand-written ## Plan with no auto-gen markers
    When I run `spur task refresh-roster <parent-wbs>`
    Then a marker-delimited roster table (WBS, Task, Status) is appended to the parent's ## Plan
    And the hand-written Plan content above it is preserved

  Scenario: Refresh is idempotent on a parent that already has a roster block
    Given a parent task whose ## Plan already contains an auto-gen roster region
    When I run `spur task refresh-roster <parent-wbs>` twice
    Then the roster region is rewritten in place with current child statuses
    And no duplicate marker region is created

  Scenario: Roster reflects current child statuses
    Given a parent with children at statuses todo and done
    When I run `spur task refresh-roster <parent-wbs>`
    Then the roster table shows each child's current WBS, title, and status

  Scenario: Refresh on a task with no children is a no-op error
    Given a task that no other task declares as parent
    When I run `spur task refresh-roster <wbs>`
    Then the command reports that the task has no children and writes nothing
```

- [ ] R1: insert a marker-delimited roster table into a parent's `## Plan` when none exists, preserving prior Plan content
- [ ] R2: idempotently rewrite the roster region in place when markers already exist (no duplication)
- [ ] R3: roster rows reflect each child's current WBS, title, and status, sorted by WBS
- [ ] R4: a task with zero children writes nothing and reports the no-op
- [ ] R5: `--json` emits the parent WBS, child count, and whether the file was written
### Design
**Chosen approach: a per-parent `refreshRoster(wbs)` method on `TaskService`, surfaced as `spur task refresh-roster <wbs>`** — mirroring `FeatureService.refresh`'s `## Tasks` marker-region pattern, scoped to one parent's `## Plan`. The global `spur task refresh` (kanban.md) is untouched.

**CLI surface (new verb):**
```
spur task refresh-roster <wbs> [--folder <path>] [--json]
```
Distinct from the global `task refresh`; targets one parent on demand. Exit 0 on write or clean no-op; 1 on error (parent not found, no `## Plan`).

**Child index (reuse 0121's shape):** scan the tasks dir for siblings whose `parent_wbs == wbs` — the same `findChildren` logic the roll-up gate uses. Collect `{wbs, name, status}` per child, sorted by WBS ascending.

**Roster render (mirror `renderTasksTable`):**
```
<!-- AUTO-GENERATED by spur task refresh-roster -->
| WBS | Task | Status |
| --- | ---- | ------ |
| 0110 | … | done |
<!-- END AUTO-GENERATED -->
```
Pipe-escape titles (reuse the `escapePipes` idiom).

**Write path (the design-defining constraint):** `MarkdownDocument.replaceMarkerRegion` **throws** when a section has no markers (verified: `markdown-document.ts:455`). A hand-written `## Plan` has no markers, so the generator must branch:
- **Markers present** → `replaceMarkerRegion('Plan', table)` — idempotent in-place rewrite (R2).
- **Markers absent** → append a marker-delimited block to the existing Plan body via `getSection('Plan')` + `replaceSection('Plan', preserved + '\n\n' + block)` — preserves the hand-written checklist above (R1).

This is the non-obvious part: unlike `feature refresh` (whose `## Tasks` ships with markers in the template), a task `## Plan` is hand-authored without markers, so the "just call replaceMarkerRegion" path is unbuildable for the common case. The insert-if-absent branch is required.

**Safety:** write through `atomicWriteAsync` (the same path feature refresh uses) — never a raw `writeFile`. A task with zero children is a clean no-op (write nothing, report it — R4); a task with no `## Plan` section errors (can't host a roster).

**Invariants:** idempotent (running twice yields the same bytes); only the marker region (or an appended block) changes — hand-written Plan content and every other section are byte-preserved; `--json` carries `{wbs, childCount, written}` (R5).

**Key signatures (verified against real types):**
```
// TaskService — new method:
async refreshRoster(wbs: string): Promise<{ wbs: string; childCount: number; written: boolean }>;
// reuses: findChildren-style parent_wbs scan; MarkdownDocument.{hasSection,getSection,replaceSection,replaceMarkerRegion,serialize}; atomicWriteAsync.
```

### Solution
Added `spur task refresh-roster <wbs>` — the generator half of the 0121 roll-up gate. Regenerates a parent's sub-task roster inside its `## Plan` between auto-gen markers, idempotently. New verb; global `task refresh` (kanban) untouched.

**Design-defining decision (per the 0121/0122 type-fit lesson):** the obvious "call `MarkdownDocument.replaceMarkerRegion` like feature refresh" is wrong twice over — (1) a task `## Plan` is hand-authored *without* markers, so the helper throws (`markdown-document.ts:455`); (2) the helper hardcodes the rewrite label to "spur feature refresh", which would mislabel a task roster. So region handling is done in the service (strip-prior-region + re-append) with `refresh-roster`-labeled markers. Verified against the real types before coding, not assumed.

**Live-corpus smoke (reverted, not committed):** `task refresh-roster 0109` on the real corpus correctly appended an auto-block below 0109's hand-written roster and was idempotent on a second run; the test mutation to 0109 was reverted (out of 0123 scope).
