### Root Cause

`plugins/sp/lib/inline-run.generated.mjs` (and the other generated plugin-lib twins) are committed
build outputs regenerated by `bun run build:plugin-lib`. Two branches that both regenerate the twin
can textually auto-merge into a twin that matches NEITHER source tree — observed live when merging
`sp/run-1049-e7e0` (1049) into `main` carrying 1048's `workflow-service.ts` changes: git merged the
twin cleanly, but the result was stale until `bun run build:plugin-lib` was re-run in the merge
resolution (2-line drift caught only because the merger knew to regenerate).

There is no automated check that a committed twin equals regeneration from the committed sources;
`plugin-smoke` (ADR-065) asserts standalone imports only, and twin parity is enforced procedurally
(release discipline), not mechanically. A stale twin ships plugin behavior that diverges from
`packages/app` sources.

### Solution

Add a freshness gate that regenerates the twins and fails on any diff against the committed files —
`bun run build:plugin-lib && git diff --exit-code plugins/sp/lib/*.generated.*` — wired into the
existing check surface that owns release integrity: the pre-release `plugin-smoke` script
(`package.json:80`, `scripts/commands/plugin-install-smoke.ts`) and/or `spur-check-feature`. The
generator entry point is `build:plugin-lib` (`package.json:60`); the gate command lives in
`package.json` `scripts` like the existing ADR-065 `plugin-smoke` enforcement.
