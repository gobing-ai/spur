## 1397. Ship upstream-fix and install-sync delegation workflows

### Background

Two recurring cross-repo chores: asking ts-libs for a facade fix and asking superskill for an install sync. With 1395 a member like `{ id: tslibs, project: ts-libs, member: coder, authEnv: … }` is reachable through the gateway, and with 1396 its receipt can be followed to completion.

**Refine corrections (2026-11-17)**
- "delegate via the cross-project address" → workflows name a member with `agent.run` (`agent: <member id>`). Transport is never user-selected (invariant 1, `a2a-member-transport.md` §4.3). → The workflows take the member id as a variable with a default (`tslibs`, `superskill`), and no URL or project appears in YAML.
- "the target creates a linked task" → the target member is an agent that receives text. A task appears only if the request tells it to create one, and the only return channel is the completed task's artifact text (the member's inbox reply, §3.5). → The request body asks for `spur task create` tagged `delegated-from:<sender-slug>:<wbs>` and a reply whose first line is `WBS: <id>`. The workflow parses that line and records it on the requesting task.
- Creating a task mutates the target tree → this is admitted, because Spur members declare `urn:spur:write-fencing:v1`. The workflow declares no `requireDiff`/`expectFiles`, so admission follows the card rule unchanged.
- Workflow YAML SSOT is `config/workflows/`, and `apps/cli/config/` is generated by `build:bundle` (AGENTS.md).

### Requirements

- [x] R1. Add `config/workflows/delegate-upstream-fix.yaml` and `config/workflows/delegate-install-sync.yaml`. Variables: `wbs` (the requesting task, required), `member` (default `tslibs` / `superskill`) and `summary` (the request text).
- [x] R2. Each workflow sends one `agent.run` to `${member}`. The prompt includes the requesting project slug, the WBS, the summary, the instruction to create a task tagged `delegated-from:<slug>:<wbs>`, and the instruction to reply with a first line `WBS: <id>`.
- [x] R3. On completion, the workflow parses `WBS: <id>` from the turn output. It records `delegated-to:<member>:<id>` as a tag on the requesting task through `spur task update <wbs> --add-tag`. A missing or malformed line fails the step and names the member and the remote task id.
- [x] R4. Both workflows pass `spur workflow validate`, and the bundle is regenerated (`bun run --filter @gobing-ai/spur build:bundle`).
- [x] R5. An e2e runs both against two fixture projects (from 1395) with a deterministic target member. It asserts that a task tagged `delegated-from:…` exists in the target and that the requesting task carries `delegated-to:…`.
- [x] R6. Add both workflows to the workflow catalogue with the member config they expect.

#### Q&A entry — 2026-11-18T06:04:48.686Z

- **How does the receipt link back to the requesting task?** Through tags at both ends (`delegated-from` / `delegated-to`) plus the sender's `coordination_runs` row from the workflow run. No new field.
- **Real ts-libs/superskill config shipped?** No. The workflows default the member ids, and declaring those members is operator config, documented in the catalogue.

### Design

**WHAT.** Two state-machine workflows built only from existing actions: `agent.run` plus a shell step for `spur task update`. No new action type.

**WHY.** Tags give both ends a cheap, CLI-gated, queryable link (`spur task list --tag …`) with no new field or schema. The `WBS:` reply line is the only return channel the A2A artifact offers.

**WHERE.** `config/workflows/delegate-{upstream-fix,install-sync}.yaml`, the generated `apps/cli/config/` (via build), the workflow catalogue doc, and the e2e beside the 1395 suite.

**Anti-patterns.**
- No URLs or projects in YAML.
- No direct corpus writes.
- Don't parse free-form replies beyond the one `WBS:` line.

### Plan

- [ ] Step 1 (test first, R5): extend the two-project e2e with a deterministic target member that creates the tagged task and replies `WBS: <id>`. Assert the tags on both ends.
- [ ] Step 2 (R1-R3): author both workflows, then `spur workflow validate`.
- [ ] Step 3 (R4/R6): rebuild the bundle and update the catalogue.
- [ ] Step 4: `bun run spur-check`.

### Solution

**Change map.**

- `config/workflows/delegate-upstream-fix.yaml`, `config/workflows/delegate-install-sync.yaml` (new) —
  two-state state machines (`request` → `record` → `done`): one `agent.run` to `${vars.member}`
  (defaults `tslibs` / `superskill`, `executor: fleet` per ADR-126), then three bounded shell steps
  that locate this run's request in the inbox, parse the reply's first `WBS: <id>` line, and write
  `delegated-to:<member>:<id>` on the requesting task through `spur task update --add-tag
  --no-lifecycle`. Vars: `wbs` (required), `member`, `summary`. No URL, project or transport appears
  in YAML; `apps/cli/config/` regenerated by `build:bundle`.
- `packages/app/src/workflow/fleet-dispatch.ts` — an A2A-shaped member (literal card OR project
  address) now receives the PROMPT TEXT in the dispatch body instead of ADR-057's pointer to a local
  artifact it cannot read, and both shapes go through the write-fencing admission (a project member
  was previously skipped by the `member.a2a` test).
- `packages/app/src/services/fleet-service.ts` — `resolveMemberExecutor` no longer sees a
  project-addressed member: `member.a2a !== undefined || member.project !== undefined` selects the
  A2A branch, so a 1395 declaration resolves without a local executor.
- `scripts/commands/delegate-workflow-e2e.ts` (new) + `scripts/spur-dev.ts` — the
  two-install proof: B's `spur serve` A2A card as the member, a deterministic exec worker that creates
  the tagged task and replies `WBS: <id>`, both workflows run for real, plus the malformed-reply
  failure leg. Invoked as `bun scripts/spur-dev.ts delegate-workflow-e2e`; no `package.json` script was
  added, because a dependency-manifest change flips the 1311 migration-ownership evidence to `no-go`. Receipt at `docs/reports/delegate-workflow-e2e-receipt.json`.
- `docs/design/configuration-contracts.md` — the workflow catalogue lists both and documents the
  expected member config (operator-declared, not shipped).
- `packages/app/tests/workflow/replay-matrix.test.ts` + `config/pipeline-budgets.json` — the two new
  definitions registered in both consumer lists (`modelQueries: 1`, wall-clock unenforced/null).

**Rationale.** Tags at both ends plus the sender's coordination row give a queryable link with no new
field, table or verb, and the `WBS:` line is the only return channel an A2A artifact offers. The
prompt-text fix is the difference between "the workflow ran" and "the member received the request":
a remote install cannot read our `.spur/run` tree.

gateway then cannot adopt it; that form is covered by 1395's gateway round-trip and resolution matrix.
