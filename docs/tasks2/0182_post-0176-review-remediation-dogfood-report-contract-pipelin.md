**Root cause of the report inconsistency (operator's primary complaint).** The report contract in `plugins/sp/skills/dogfood-testing/references/report-template.md` mandates six fixed headings (Testee → Execution Summary → Monitor Ledger → What We Did → Issues → Findings), a mandatory `### 3. Monitor Ledger`, recomputable cache math, per-finding feasibility tags, and a mandatory `── Dogfood Summary ──` footer. Reports 0176/0177 (driven through the sp:dogfood-testing protocol) follow it; reports 0178–0181 (written by wave-executing Codex sessions after manual timeout recovery) each use a different ad-hoc format and drop every mandatory component. Three gaps let this happen:

1. **Enforcement checks existence, not structure.** `plugins/sp/agents/super-coder.md:241` — terminal gate #5 is `ls docs/dogfood/ | grep <date-or-slug>`. Any freeform file passes.
2. **The Codex path has no teeth.** super-coder says "delegate to `Skill(skill=\"sp:dogfood-testing\", args=\"<testee> --save\")`", but Codex has no `Skill()`; the platform note degrades to "invoke the protocol directly" and nothing names the mandatory headings there. Report sizes decayed monotonically across sessions: 7.6 KB → 5.4 KB → 3.0 KB → 2.4 KB → 2.2 KB → 1.3 KB.
3. **Nothing can test the reports.** `docs/dogfood/` is gitignored (`.gitignore:155`), so no structure test can cover them — and the July-2 reports were silently never committed while committed task files (0176 §References) link to them. The ~40 June reports are tracked only because they predate the ignore.

Buglog cross-reference: bug-749 (report contract violations, this review), bug-750 (HITL cancel regression, this review); prior related: bug-742 (nested pipeline recursion), bug-744/746/748 (implement timeouts), bug-747 (`--folder` threading residual).

#### Finding detail (evidence for implementation — read before coding)

**G1 — task-pipeline HITL cancel regression (bug-750).** Wave A (task 0177) changed `packages/app/src/workflow/actions/hitl-confirm.ts:47`: cancel previously returned `{ ok: false, error: 'hitl.confirm cancelled' }` (onEnter action failure → run halts → fail-safe); it now returns `{ ok: true, data: { answer, cancelled }, setVars: { __hitlAnswer: 'cancel' } }` so workflows can route cancel explicitly. Wave A R3 routed answers ONLY in `idea-pipeline.yaml` (guards at :300–:403) and `planning-pipeline.yaml` (:143–:197). `task-pipeline.yaml` was out of R3 scope but contains the third `hitl.confirm` site (`approve` state, :123, prompt "Approve task ${vars.wbs} to proceed to verification?"). Its single outbound transition `approve → verify` is `guard: { kind: always }`; the file declares no `__hitlAnswer` var and has no `cancelled` state. Net effect: in interactive mode (`profile != auto`), answering **no or cancel at the approval gate proceeds to verification as if approved**. The gate is decorative — the exact F6 bug class Wave A existed to fix, made strictly worse for this pipeline (cancel used to abort the run; now it approves).

**G2 — implement timeout, 100% failure rate (bugs 742/744/746/748).** `stepTimeoutMs: "600000"` (`task-pipeline.yaml:40-41`, overridable via `--vars '{"stepTimeoutMs":...}'`) applies uniformly to all four `agent.run` steps. Every 2026-07-02 pipeline dogfood run failed in `implement` at that budget: run `34233eec-d3ed-44c8-9030-e0b813fb03b5` (0177, 601,064 ms), `1b7049d2-1073-4d4d-a97a-47e299bc316e` + nested `pipeline-0178` (0178, ~600 s each — the implement agent recursively launched a duplicate pipeline for the same WBS via `/Users/robin/node_modules/@gobing-ai/spur/spur.js`), `66561133-64cc-4e93-92d4-2aa8413305d6` (0179, 600,845 ms), `4ac8a861-6233-4e19-ad43-595d99bec537` (0180, 600,846 ms), `10ab1085-a744-4e10-aee2-6682b062f550` (0181, 600,942 ms). Wave D's "prompt slimming" was scoped to idea/planning/wrapup pipelines (F8) — the task-pipeline implement prompt (`/sp:dev-run --mode implement ${vars.wbs} --auto`) was never slimmed, and bug-748 explicitly confirms recurrence AFTER Wave D landed. The anti-recursion rule ("this step must NOT call /sp:dev-run in full mode … that command DRIVES this pipeline") lives only in the YAML `description:` block (~:69-71), which is never sent to the spawned agent. Consequences: (a) no run has ever reached verify/record, so Wave C's tightened verifier is unproven in-pipeline (0179 finding DF-0179-4 admits R7 proof remains partial); (b) every timeout loses machine-readable context — recovery each wave was manual archaeology over the working tree.

**G3 — verdict vocabulary drift.** `report-template.md` §2 verdict rule: PASS = every step ran, no unresolved issue; PARTIAL = ran to end with ≥1 unresolved; FAIL = the run could not complete. The testee in waves A–E was `task-pipeline.yaml` itself; it FAILed at implement every time. Reports say: 0177 "PASS WITH RECOVERY", 0178 "PASS with direct fixes applied", 0179/0180 "PASS with manual recovery; dogfood pipeline failed before verifier", 0181 (no verdict line at all). None of these values exist in the vocabulary, and all conflate "the task got done (manually)" with "the testee passed". Signal integrity cost: a reader scanning verdict lines sees five green runs where the pipeline actually went 0-for-5.

**G4 — unchecked boxes in done tasks.** `docs/tasks2/0178_*.md` — 14 unchecked boxes (Requirements R1–R5 at :33–:37; Plan P1–P9 at :79–:87). `docs/tasks2/0179_*.md` — 23 unchecked (Requirements R1–R7+supplementary at :36–:43; Plan P1–P15 at :109–:123). Both tasks are `done`; the work they describe is verifiably complete (traced during this review). super-coder terminal gate #1 (`grep -c '^\s*- \[ \]' <task-file>` must print `0`) was skipped in the manual-recovery flow. `spur task check` passed both at done — there is no L-rule for unchecked boxes at terminal status (product gap or intentional; operator decision Q3).

**G5 — no machine enforcement of the report contract.** See root-cause block above. The fix surface is two files: `plugins/sp/agents/super-coder.md` gate #5 (replace the existence-only `ls | grep` with structural greps) and `plugins/sp/skills/dogfood-testing/SKILL.md` Codex/OpenClaw/OpenCode/Antigravity platform note (name the six mandatory headings + ledger + footer inline so a session without `Skill()` still sees the contract).

**G6 — dogfood evidence trail is gitignored.** `.gitignore:155` = `/docs/dogfood`. `git ls-files docs/dogfood/` shows ~40 tracked reports (2026-06-24 → 2026-07-01, committed before the ignore); all six 2026-07-02 reports are untracked and invisible to `git status` (ignored), so nobody noticed they never got committed. Committed corpus references them: 0176 §References lists all six paths; 0177–0181 §References likewise. super-coder.md:196 calls `docs/dogfood/` "the durable evidence trail". Either the ignore goes, or the references and the "durable" wording go — the current hybrid is self-contradictory.

**G7 — arithmetic/field defects in the two compliant reports.** 0177 (`2026-07-02-sp-super-coder-0177-wave-a-dogfood.md`): ledger rows sum to fresh 12,600 (900+1,700+5,400+2,700+1,900) + cached 6,400 (600+800+2,100+1,700+1,200) = 19,000 total → 34% — but §2 claims ~22,000 total / ~8,200 cached / 37%, and the report's own "Cache calculation" line asserts round(8200/22000)=37. `report-template.md` §3: "The aggregate cache line in §2 must equal the ledger formula … If it does not, the report is invalid." Also missing from 0177: §1 `Testee agent`/`Mode` lines, §2 `Steps`/`Wall-clock`/`Fix attempts` lines; the footer omits the `Findings (P1+P2)` sub-list ("never omit a sub-list"); one finding carries `[fixed]`, which is not a legal feasibility tag (`[feasible]`/`[stale]`/`[unverifiable]`). 0176: §6 P3 finding says "aggregate cache was ~43%" while §2 + footer say ~36% (the ledger-consistent value IS 36%: cached 5,500 / total 15,200); §2 wall-clock "~35 min" vs ledger row sum 41 min (6+7+2+5+14+7). IMPORTANT anti-drift constraint: do NOT retro-fabricate Monitor Ledgers for 0178–0181 — the live-ledger rule (`monitor-ledger.md` anti-fiction section) forbids reconstruction from memory; annotate them as non-conforming legacy instead.

**G8 — CHANGELOG placement.** `CHANGELOG.md` version headings: `[0.2.12] — 2026-07-01` (line 3), … `[Unreleased]` (line 288 — BELOW all releases, inverted from Keep-a-Changelog convention; likely why agents keep appending at the top). The uncommitted diff adds "Verification depth tightened" (Wave C) and "Feature wrap-up lifecycle walk centralized" (Wave D) into the RELEASED 0.2.12 block (~:41–45) — retroactive edits to a shipped section (commit 7fffe19 had just aligned 0.2.12 with the shipped plugin) — while the Wave B entry ("Decomposition wiring …") landed correctly under `[Unreleased]` (~:297). Waves A (hitl cancel semantics, `file.read.into-var` builtin, idea-pipeline guard hardening) and E (`agent doctor` precheck, `--design-approved` wrapper flags, verbs.md facade additions, hook guard versioning + tests) have no entries anywhere despite user-visible behavior changes.

**G9 — hook guard wiring ambiguity (N3 residue).** `plugins/sp/hooks/hooks.json` PreToolUse command is `superskill hook run sp task-write-guard` (timeout 10). Wave E rewrote `plugins/sp/hooks/task-write-guard.ts` into a self-contained guard (delegates ownership to `spur task resolve --strict --json`, fail-open, `SPUR_WRITE_GUARD=off` escape hatch) with 10 passing tests — but its own header admits "Installed hook configs still use the portable `superskill hook run sp task-write-guard` entrypoint". Open questions: does superskill actually execute THIS script (or its own vendored copy → drift risk)? On machines without superskill the guard silently no-ops (the original N3 concern, unresolved). Context: the 0181 partial diff tried `${CLAUDE_PLUGIN_ROOT}` as the command and was reverted for portability (0181 report P3) — so both options have known costs; this is a real operator decision (Q2), not a mechanical fix.

**G10 — `file.read.into-var` absolute-path bug.** `file-read-into-var.ts:57`: `const resolved = joinPath(context.workdir ?? '.', rawPath);`. ts-runtime's `joinPath` (`~/xprojects/ts-libs/packages/runtime/src/path.ts:83-89`) filters/normalizes and joins ALL segments — absoluteness is taken from the FIRST segment only, so `joinPath('/work', '/tmp/x')` → `/work/tmp/x`. The action docstring implies absolute paths work ("Relative paths resolve against context.workdir"). Latent today (bundled workflows pass only relative `.spur/run/...` paths). Fix: `isAbsolutePath(rawPath) ? normalizeSeparators(rawPath) : joinPath(...)` (both helpers exported by `@gobing-ai/ts-runtime`), or `resolvePath`. One new test case.

**G11 — copy-paste JSDoc.** `task-service.ts` ~:562: the JSDoc above `async batchCreate(...)` reads "Per-parent summary produced by the post-create wire-up pass …" — that describes the `ParentWireResult` interface (whose own doc it duplicates), not the method. Cosmetic; fix wording only, no behavior.

**G12 — uncommitted five-wave tree.** `git status` at review time: ~50 modified/added files, +2,173/−387, all on `main`, including all product code, workflow YAML, plugin docs, ADR-029, and the 0176–0181 corpus.
