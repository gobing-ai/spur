## 0178. 0176 Wave B: decomposition wiring and parent readiness

### Background

Child task for 0176 Wave B. Fix decomposition wiring findings F1 and F2: roster automation exists but is unwired, decomposed parents remain executable todo tasks, and ready resolution can pick umbrella parents.

### Requirements
- R1. Make batch-created child tasks refresh the parent sub-task roster for each distinct `parent_wbs` after atomic creation.
- R2. Transition decomposed parents from `todo` to `wip` through lifecycle-aware code, surfacing guard denials clearly.
- R3. Exclude parent tasks with open children from the `ready` batch selector documented in `execution-batch.md`.
- R4. Update decomposition and planning skill prose to describe shipped roster automation and the shipped roll-up gate.
- R5. Add service/CLI coverage proving parent roster refresh is idempotent after batch creation.
### Acceptance Criteria
Given Wave B (decomposition wiring) of 0176. The parent roster generator (`spur task refresh-roster`, task 0123) and the L4 roll-up gate (task 0121) are both shipped in the service layer but the skill prose and the `batch-create` pipeline still treat them as deferred/manual. Wave B closes that gap end-to-end so that `/sp:dev-runall --tasks ready` can never pick a parent that "implements nothing" (decomposition.md definition) and so the L4 gate's "roll-up drift" finding becomes structurally impossible at the moment of decomposition.

- [x] **R1 (F1) — auto roster refresh on batch-create.** When `TaskService.batchCreate` finishes an atomic create, for every **distinct** `parent_wbs` referenced by the batch, the service invokes `refreshRoster(parentWbs)` before returning. The roster block is the same marker-delimited, idempotent block `refreshRoster` already produces. Distinct = deduplicated (a batch of 5 children with `parent_wbs: 0042` invokes `refreshRoster('0042')` exactly once; a batch spanning two parents invokes it twice, once per parent).
- [x] **R2 (F2) — parent transition through lifecycle verb.** The same `batchCreate` path additionally transitions each referenced parent `todo → wip` via `writeService.transition` (the lifecycle-guarded verb), not by raw frontmatter edit. If a parent is already `wip` or later (`done` / `testing` / `blocked` / `cancelled`), the transition is **skipped silently** — the engine treats `currentStatus === wip` as a no-op via `requestTransition` (the lifecycle port returns `{ allowed: false, report: 'already in this status' }` — we treat that as success, not failure). Any **other** denial (illegal target, missing task) surfaces as a thrown error with the guard report in the message; the batch's atomic-create phase has already committed, so the error is raised from the post-create step and the CLI surfaces it after the children are written.
- [x] **R3 — `ready` selector excludes umbrella parents.** `plugins/sp/skills/spur-dev/references/execution-batch.md` Step 1 `ready` resolution gains an explicit exclusion rule: a `todo`/`backlog` candidate whose `spur task list` shows at least one child task (any non-done/non-cancelled descendant) is dropped from the `ready` set with a report line. The behavior is documented in the reference and the reporting line is described in the report-shape examples.
- [x] **R4 — skill prose reflects shipped state.** `plugins/sp/skills/spec-decomposition/references/decomposition.md` parent-task section: the "maintained by hand today" sentence is rewritten to reference `spur task refresh-roster`; the "deferred roll-up task" line is updated to call out 0121 as shipped. `plugins/sp/skills/spur-dev/references/planning-workflow.md` Step 5 paragraph is replaced with: "the parent's sub-task roster is auto-generated by `spur task refresh-roster` — invoked from `batch-create` per distinct `parent_wbs` after the atomic create lands."
- [x] **R5 — service test for idempotent parent roster after batch-create.** New test in `packages/app/tests/services/task-service.test.ts` (extends the `batchCreate` describe block): given a parent task with a `## Plan` section and a `parent_wbs` batch item, calling `batchCreate` results in (a) the parent file containing the marker-delimited roster with the new child row, (b) `wip` status in the parent's frontmatter, and (c) a second `batchCreate` call (different child, same parent) leaves the roster in a single, valid marker region with both children listed (idempotent re-run of `refreshRoster`).

### Design

Three surgical changes, all service-side or skill-prose. No schema changes, no engine changes, no new CLI verbs.

**1. `TaskService.batchCreate` — post-create parent wiring (R1, R2).** After the atomic create loop completes successfully, collect the set of distinct `parent_wbs` values from the input items (filter out `null`/`undefined`/empty), then in stable order:

- For each parent, call `this.refreshRoster(parentWbs)` — already idempotent; the second-call behavior is verified in the existing `refreshRoster` tests (R2 idempotency row). If the parent has no `## Plan` section, `refreshRoster` throws; the error propagates to the caller.
- For each parent, attempt `this.writeService.transition({ kind: 'task', id: parentWbs, filePath: ..., folder: this.ctx.tasksDir }, 'wip', 'system')` — but **only** if the parent's current status is `todo` (read it via `this.show(parentWbs)` or by parsing the file). Skip silently otherwise. We check status before calling `transition` to avoid the `requestTransition` "already in this status" denial path polluting the logs; the SchemaLifecyclePort's no-op return is treated as success, but the cleaner path is to not call it at all.

Both post-create steps run after all children are written; on failure of one parent, the other parents in the set are still attempted (best-effort, not all-or-nothing — the children are already on disk and rolling them back is worse than reporting a partial wire-up). The CLI surfaces a final summary listing each parent, the action taken (rostered/transitions/no-op/error), and any error messages.

**2. `execution-batch.md` `ready` selector (R3).** Update the Step 1 table row for `ready` and add a new short subsection between "Dedup" and the "`ready` edge note" describing the umbrella-parent exclusion. Each excluded parent is reported in the batch report's per-task outcome list with a one-line reason referencing the open children. No service change — this is purely a skill-prose rule the `sp:super-coder` orchestrator follows.

**3. Skill prose (R4).** Two edits: `decomposition.md` parent-task section and `planning-workflow.md` Step 5. Surgical — replace the specific stale sentences, do not restructure the surrounding sections.


- **Post-create, not in-transaction.** The roster refresh and parent transition run *after* the children are written. If a partial write happens, the children exist but the parent's roster is stale. Acceptable because (a) the batch is atomic at the create level — either all children land or none do, (b) the parent transition failure path raises loudly so the operator can re-run `spur task refresh-roster` and the transition manually, and (c) a transactional cross-entity write would require an engine-level parent/child transaction primitive that does not exist.
- **Skip parent transition when not `todo` vs. catch the engine denial.** Catching the denial feels more uniform (one code path), but it produces noisy logs on re-runs and couples the service to the lifecycle port's exact denial message. The pre-check is one extra file read per parent and is clearer.
- **`refreshRoster` error propagates vs. swallowed.** A parent without `## Plan` is a corpus bug we want to surface — the L4 gate already warns on a parent with children but no roster. Propagating the error matches the gate's intent.
- **No CLI flag.** The wiring is unconditional. The previous "hand-write the roster" workflow was the only escape hatch, and `spur task refresh-roster` is already the user-facing escape hatch for re-runs.


- `refreshRoster` is **idempotent** (R2 in task 0123) — calling it twice on a parent produces one marker region, not two.
- `writeService.transition` enforces the **lifecycle guard** (R3 in planning-write-service) — illegal target statuses are rejected, the parent's file is not written.
- The post-create steps touch parent files only; child files written by `createBatchItem` are not reopened or modified.
- All four public mutation paths (`create` / `update` / `transition` / `updateField` / `updateStatus`) on `TaskService` are unchanged except `batchCreate` — single point of difference, no surface-area drift.
